# Lerch Prototyping: Data Foundation & Invariants

## 1. Guiding Principle: Shared Vocabulary, Open Implementation

Prototypes in `tc-proto-docker` share a **semantic domain contract**, not a rigid physical schema:

- **Invariants define the simplest baseline:** Every prototype agrees on *what core concepts exist*, *why they exist*, and the *minimum fields* they carry.
- **Refinement introduces complexity:** Whenever a concept can start simple (e.g., a blocker as a `severity` field on an item, or an artifact referenced by ID on an item) and grow into a richer structure (e.g., a directed dependency graph or junction tables), the baseline invariant stays simple.
- **Runs own their storage and seeding:** Each prototype run (`prototypes/run-XXX/`) owns its isolated database (`proto_run_XXX`) and its seed script (`server/seed.ts`). Everything beyond the minimum invariants is open for the run to decide based on the question its brief investigates.

## 2. Core Domain Invariants (Entity Level)

These 8 core conceptual groups define Lerch's shared domain vocabulary:
- **Always-on Baseline (Groups 1–4):** `Space`, `Actor`, `Item`, and `Hierarchy` are present in every prototype run.
- **On-Demand Invariants (Groups 5–8):** `Blocker`, `Tag`, `Artifact`, and `Event` define the standard invariant shapes whenever a prototype brief or dataset includes them.

| Core Group | Purpose (Why it exists) | Minimum Invariant Fields (Simplest baseline) | Refinements & Extensions (When a run needs more) |
|---|---|---|---|
| **1. Space** (`spaces`) | Organizational or personal perimeter containing work and members. | `id`, `name`, `type` (`personal` \| `organization`) | Access policies, administrator/member permission rules, space-level view configurations. |
| **2. Actor** (`actors`) | Any entity that acts in the system—both human users and autonomous agents. | `id`, `name`, `kind` (`human` \| `agent`), space memberships | Human account extensions (`email`, password/OAuth/2FA credentials, `avatar`, `bio`, `api_keys`), explicit space roles (`admin`, `member`). |
| **3. Item** (`items`) | The fundamental unit of work or goal at any scale (`project`, `epic`, `story`, `task`). | `id`, `space_id`, `title`, `state` (`unstarted` \| `started` \| `done` \| `discarded`), `created_at`, `updated_at` | Scale/type (`project` \| `epic` \| `story` \| `task`), `description`, `contributors` / `lead`, `effort`, `scheduled_time`, item `score` (`doesn't work`, `bare minimum`, `satisfactory`, `excellent`), visual board placement (`column` / `kanban`, `position`), on-item references (`parent_id`, `tags`, `artifacts`, `blocker`). |
| **4. Hierarchy** (`relations`) | Recursive decomposition of work—any item can break down into child items; nesting a `task` under a `task` is what makes it a subtask. | `parent_id` (linking a child item to its parent) | Dedicated parent-child relation records/tables, sibling ordering. |
| **5. Blocker** (`blockers`) | Surfacing what stops work from proceeding and triaging how urgent it is. | `severity` (`cannot do anything`, `will be stuck`, `slowed down`, `nice to have`) | Directed dependency record (`blocker_item_id` blocks `blocked_item_id` with `severity`), cross-project dependency resolution. |
| **6. Tag** (`tags`) | Cross-cutting markers that categorize and connect items. | `id` (or slug), `name` | `space_id` (space-scoped vs. global tags), `color`, autogenerated tags. |
| **7. Artifact** (`artifacts`) | External links or uploaded files attached to work. | `id`, `title`, `kind` (`link` \| `file`), `uri` (URL/path or file reference) | Linked from items via `artifact_ids` or a join table; file upload metadata (MIME type, size), knowledge-base linkage. |
| **8. Event** (`events`) | Append-only log of actions over time, driving history, analytics, and notifications. | `id`, `space_id` (optional), `target_id`, `actor_id`, `type`, `created_at`, `changes` / `payload` (optional) | Per-recipient notification `read` state, `target_kind` discrimination across items, spaces, and social events. |

## 3. Architectural Dimensions Open to the Prototype Run

Everything outside the semantic invariants above is intentionally open for each prototype run to decide and evaluate:

| Dimension | Open to the Prototype Run |
|---|---|
| **Storage Engine** | PostgreSQL (`DB=postgres`), MongoDB (`DB=mongo`), Hybrid relational + document (`DB=hybrid`), SQLite/PGlite, or in-memory/KV storage (`DB=none`). |
| **Schema Shape (Normalized vs. Embedded)** | **Relational:** Separate normalized tables and join tables (`item_tags`, `item_artifacts`, `blockers`, `relations`, `members`).<br>**Document / Simple:** Embedded arrays and fields directly on the Item document (`item.tags`, `item.artifact_ids`, `item.blocker_severity`). |
| **Hybrid SQL / NoSQL Intersection** | How ownership, space membership rules, and search queries bridge relational and document stores when testing `DB=hybrid`. |
| **Identifier Format** | UUID, ULID, human-readable fixture slugs (`item-bread-knife`), integer sequences, or MongoDB `ObjectId`. |
| **Board & View Representation** | Whether board columns are stored as a `columns` table, configured on a `space`, or represented as a string/field on items, and how other views (Gantt, Timeview, Calendar, Mind-Map, Widget Grid) query them. |
| **Social & Platform Modules** | Prototypes exploring User Management, Social, or Public API features introduce `Friendship` (`requester_id`, `addressee_id`, `status`), `Message` / `Comment` (`id`, `author_id`, `target_id`, `body`, `created_at`), `Notification` read tracking, or `ApiKey` records as needed. UI or storage runs that do not test these modules omit them. |
| **Data Access Layer** | Direct database driver queries (`pg`, `mongodb`), Nitro server utility modules (`server/utils/`), or an ORM. |
| **Seeding (`server/seed.ts`)** | Each run defines its own idempotent `prototypes/run-XXX/server/seed.ts`, seeding the baseline fixtures (such as the Dinner fixture or 10k-item benchmark set) plus any custom fields its brief requires. |
