# run-511: Social Graph, Friendships & Private Chat Persistence

**Kind:** exploration  
**Port:** 3511  
**DB:** postgres  
**Question:** How should the bilateral social graph (`Friendship` state machine) and 1-to-1 private chat (`Message`) be persisted, partitioned, and indexed in PostgreSQL without coupling to the core task domain, can chat be strictly gated to accepted friends without breaking cross-organization collaboration, and how do friend removal, WebSocket disconnects, and notification fan-out interact with message history and active sessions?

## Scenario

A development team with a C/C++ systems background is evaluating the social and communication architecture required for the `ft_transcendence` platform (`W3` User interaction: friends, profiles, chat; `U1` User profiles and online status; `W2` WebSockets; `W6` Notifications). In Lerch, the core domain is intentionally lean and focused on work decomposition (`Space`, `Actor`, `Item`, `Hierarchy`). Social relationships and direct communication are essential for evaluation requirements but must not compromise the integrity, scalability, or data boundaries of the primary task engine (`§2.9 Q5`, `§3.4 Q1`).

The developer launches the diagnostic testbed at `http://localhost:3511` to evaluate schema isolation, access control policies, and real-time persistence mechanics across four interrelated workflows:

1. **Friendship State Machine & Relational Integrity:**
   The developer inspects and tests the lifecycle of a `Friendship` record (`pending` $\to$ `accepted` $\to$ removed/declined) between human actors. The interface verifies database-level invariants:
   - Ensuring uniqueness regardless of invitation direction (preventing inverse duplicate rows when User A requests User B while User B requests User A) using canonical ordering constraints (e.g. `LEAST(requester_id, addressee_id), GREATEST(...)`).
   - Enforcing self-friending rejection (`CHECK (requester_id <> addressee_id)`).
   - Evaluating whether friend requests record state transitions in the immutable `events` log (`§3.4`).

2. **Chat Policy Enforcement & Organization Scope (`§2.9 Q2`):**
   The developer simulates communication between seeded actors representing distinct social relationships:
   - *Alice & Bob:* Mutual accepted friends.
   - *Alice & Charlie:* Pending friend request sent by Alice.
   - *Alice & Dana:* Teammates sharing an organization space (`Engineering`), but not mutual friends.
   - *Alice & Evan:* Platform strangers with no shared spaces and no friend relationship.
   
   The developer toggles between two access control policy modes in real time to assess query performance and behavioral fit:
   - *Policy Mode A (Strict Friend-Only Chat):* Direct messaging requires an explicit, mutual `status = 'accepted'` friendship. Unconnected users and pending requests receive an immediate `403 Forbidden` response.
   - *Policy Mode B (Shared-Organization Exception):* Direct messaging is permitted if the actors share at least one common organization space (`Space` where `type = 'organization'`), allowing workplace collaboration without requiring personal friend links.
   The developer observes the SQL authorization lookup overhead for each message and tests failure boundaries when non-permitted users attempt to initiate chat sessions.

3. **Friendship Severance & Session Tear-Down:**
   While two users are actively chatting over real-time WebSockets (`W2`), the developer triggers a "Remove Friend" action. The prototype evaluates the immediate operational impact and allows comparing three chat history retention strategies:
   - *Strategy 1 (Read-Only Archive):* The active WebSocket room is immediately closed, and further outbound messages are blocked. Existing message history is retained for both users in an immutable, read-only state.
   - *Strategy 2 (Tombstoned / Hidden Thread):* The thread is marked inactive and hidden from active inboxes, reappearing only if mutual friendship is re-established.
   - *Strategy 3 (Cascade Hard Purge):* The message thread and all related records are transactionally deleted upon friendship severance.

4. **Message Storage, Indexing & Chronological Pagination at Scale:**
   The developer benchmarks 1-to-1 message storage using a pre-seeded conversation thread of 10,000 to 50,000 messages. The developer evaluates:
   - *Compound Indexing Layout:* Assessing composite indexes on `(LEAST(sender_id, recipient_id), GREATEST(sender_id, recipient_id), created_at DESC)` versus paired directional indexes.
   - *Pagination Ergonomics:* Directly comparing **Keyset Cursor Pagination** (`WHERE created_at < :cursor ORDER BY created_at DESC LIMIT :n`) against traditional **Offset Pagination** (`OFFSET :n LIMIT :m`) under deep pagination, measuring query execution time (`EXPLAIN ANALYZE`), buffer cache reads, and stability when new messages arrive concurrently.

5. **Real-Time Transport, Online Presence & Notification Debounce (`W2`, `W6`):**
   The developer connects dual simulated browser sessions to test live message delivery over Nitro WebSockets, presence heartbeats (broadcasting online/offline status transitions to mutual friends), and offline notification fan-out. When a recipient is disconnected or inactive, inbound messages trigger unread indicators. The developer tests a 30-second debounce window that consolidates bursts of rapid consecutive messages into a single notification event rather than producing noisy notification floods (`§2.9 Q4`).

Rich-text formatting, media attachments/file uploads (`kind: "file"`, deferred to `run-512`), group channels, audio/video streaming, and full kanban boards are intentionally omitted to keep this prototype strictly focused on relational social persistence, WebSocket lifecycle management, and policy enforcement boundaries.

## What to Evaluate

### 1. Visual & Presentation Aspects (Diagnostic Tooling)
- **Multi-Persona Social Switcher:** A split diagnostic interface allowing the developer to simulate Alice, Bob, Charlie, Dana, and Evan simultaneously, observing live message feeds, friend status badges, and presence indicators in real time.
- **Social Graph & Policy Inspector:** A visual table displaying existing `friendships`, active memberships in organization `spaces`, and current policy rules, with clear indicators of why a direct message is permitted or denied.
- **WebSocket Frame & Event Log:** A live diagnostic feed capturing inbound and outbound WebSocket frames (`chat:send`, `chat:message`, `presence:status`, `error:forbidden`), displaying message payload structures, delivery latencies, and connection states.
- **SQL & Query Plan Inspector:** Side-by-side display of the raw SQL queries executed for friendship validation, message insertion, and conversation pagination, showing execution times, parameter bindings, and `EXPLAIN ANALYZE` query plans.

### 2. Procedural / Workflow Aspects
- **Policy Verification Overhead:** The procedural friction and latency of executing friendship and organization authorization checks on every message submission. Assessing whether checking friendship status in SQL middleware introduces noticeable delay.
- **Friendship Lifecycle Transitions:** The operational flow of sending, accepting, declining, and cancelling friend requests, verifying that race conditions (such as simultaneous inverse requests) resolve cleanly without deadlocks or duplicate records.
- **Pagination Stability During Active Chat:** The developer experience when scrolling backward through message history while new messages are being sent, confirming that cursor-based keyset pagination prevents duplicate rows or skipped messages.
- **Severance Handling:** How intuitively the application handles friendship termination during active communication, verifying that socket rooms are torn down cleanly and that the UI communicates the read-only or severed state without crashing.
- **Notification Debouncing Ergonomics:** The behavior of notification fan-out during rapid typing, confirming that offline users receive grouped alerts without flooding their notification inbox.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **Relational Chat Store in PostgreSQL (`§2.9 Q2`):** Does a normalized PostgreSQL `messages` table with compound indexing deliver sub-5ms read and write latency across 50,000 messages, confirming that dedicated NoSQL or document databases are unnecessary for 1-to-1 chat in Lerch?
- **Domain Schema Isolation (`§2.9 Q5`, `§3.4 Q1`):** Demonstrating that `friendships` and `messages` exist as self-contained satellite tables with foreign keys to `Actor(id)`, without coupling to `Item`, `Space`, or `Hierarchy`.
- **Nitro WebSocket Architecture (`crossws` / native WS):** Evaluating the developer ergonomics of establishing authenticated user-specific WebSocket connections, joining dynamic 1-to-1 rooms, handling heartbeat disconnects, and broadcasting friend presence inside Docker containers.
- **Cursor vs. Offset Query Performance:** Quantifying the performance divergence between keyset pagination and `OFFSET` queries over large message datasets for developers accustomed to predictable memory access patterns.
