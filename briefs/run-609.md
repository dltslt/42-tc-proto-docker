# run-609: Social Hub: Friends Presence Drawer, User Profiles & 1-to-1 Chat

**Kind:** interaction-lab  
**Port:** 3609  
**DB:** none  
**Question:** How can Lerch integrate mandatory 42 `ft_transcendence` social features—user profiles (`U1`), friend requests and live presence tracking (`W3`), and persisted 1-to-1 private chat (`W3`) alongside TOTP 2FA enrollment (`U6`) and API key management (`W4`)—without cluttering the quiet "butler" workspace, and how should the UI differentiate direct chat with accepted friends from collaboration with non-friend colleagues inside the same organization space (`§2.9 Q2`, `§2.9 Q5`)?

## Scenario

A team of developers with a C/C++ systems background is implementing the social interaction and user profile foundation for Lerch in Nuxt 4, satisfying the mandatory and bonus module requirements of 42 `ft_transcendence`: Standard User Management and Profiles (`U1`), OAuth 2.0 Profile Linking (`U3`), Complete 2FA (`U6`), User Interaction: Chat, Profiles, Friends (`W3`), and Personal API Key Management (`W4`).

In Lerch's product vision (`specs/product-short-v2.md`), the application acts as a quiet, distraction-free "butler" for team task and project coordination: it stays out of the way, and an ordinary change takes the fewest steps. In contrast, the 42 `ft_transcendence` curriculum mandates full-fledged social connectivity: customizable user profiles with avatars, peer-to-peer friend requests, live online/offline presence indicators, and a persistent 1-to-1 direct messaging (DM) chat system. If social widgets and persistent chat boxes dominate the workspace, Lerch devolves into an intrusive communication tool that distracts from core task execution. Conversely, if social tools are overly concealed or fragmented, the application fails the evaluation requirements.

The developer launches the prototype at `http://localhost:3609` backed by an in-memory reactive store (`DB=none`) loaded with a curated five-persona fixture (`Alice`, `Bob`, `Charlie`, `Dana`, `Evan`). These personas reflect realistic social and organizational states: mutual friendships, pending friend requests, colleagues sharing an organization space who are not friends, and varying online presence states. Through a diagnostic multi-persona switcher and interactive control toggles, the developer explores three core architectural and interaction questions:

1. **Workspace Spatial Ergonomics & Social Presentation (`§2.9 Q5`):**
   The developer evaluates how interpersonal communication coexists with the core task board by directly comparing two presentation architectures:
   - *Pattern A (Quiet Butler Slide-Over Drawer):* The primary work surface (a 3-column kanban board with task breakdown drawers) remains completely clean and task-focused. In the global header, an unobtrusive social pill displays the active user's avatar, unread message badges, and an aggregate online presence indicator (e.g. green dot + "3 friends online"). Clicking the pill or pressing `Cmd+U` / `Ctrl+U` smoothly opens a right-hand slide-over drawer housing the complete Social Hub: **Friends** (with status dots and 1-click chat launch), **Requests** (incoming/outgoing friendship actions), **Directory** (organization colleagues), and **Profile & Security** (avatar, bio, OAuth badge, 2FA QR enrollment, and API keys).
   - *Pattern B (Docked / Floating Chat Console):* A traditional bottom-docked persistent chat bar (similar to LinkedIn or Facebook), where active friend chats pop up as floating docked windows over the kanban board, allowing users to type messages while concurrently dragging cards across columns.
   The developer assesses visual distraction, screen real estate utilization, and context-switching friction between both modes.

2. **Work Communication vs. Interpersonal Social Chat (`§2.9 Q2`):**
   The prototype clearly distinguishes between the two communication primitives in Lerch:
   - *Item Comments (`Comment`):* Space-scoped, item-anchored chronological discussions visible to all contributors of that work unit, surfaced directly on the item detail drawer.
   - *Private Messages (`Message`):* Interpersonal 1-to-1 real-time conversations between specific human actors (`W3`), conducted entirely inside the Social Hub or chat panel.
   The developer tests opening an item detail drawer to post task comments, verifying that project discussions remain anchored to work items while private social chatter is kept strictly inside the user-to-user messaging stream.

3. **Friendship Policy Matrix & Organization Directory Triage (`§2.9 Q2`):**
   In Lerch, Organization Spaces (`U5`) group coworkers, but `Friendship` is an independent peer-to-peer relationship (`§2.9`, `specs/data-foundation.md`). The developer tests how the UI presents organization colleagues who are not accepted friends, toggling between two policy rules:
   - *Policy 1 (Strict Friends-Only DM Gate):* Private 1-to-1 chat is strictly restricted to accepted friends. When viewing a non-friend colleague in the shared organization directory, their card displays their profile, shared projects, and an "Add Friend" action, with chat locked until the friendship is accepted.
   - *Policy 2 (Open Organization Direct Messaging):* Any member sharing an organization space can initiate a direct 1-to-1 message, with the directory clearly categorizing contacts into "Friends" (with live presence dots) and "Organization Colleagues".
   Using the persona switcher, the developer simulates sending a friend request from Alice to Dana, switches to Dana to accept the request, and observes the immediate real-time unlocking of presence dots and chat capabilities.

4. **Complete Profile, 2FA Enrollment & API Key Surface (`U1`, `U3`, `U6`, `W4`):**
   The Profile tab provides a comprehensive personal security and configuration panel:
   - Editable display name, unique email, and bio.
   - Interactive avatar image uploader with format/size validation and default SVG fallback.
   - Linked OAuth 2.0 provider status card (`U3`, e.g. "Linked to 42 School as `mweber`").
   - Complete Two-Factor Authentication (`U6`) enrollment wizard: interactive QR code generation for TOTP authenticator apps (Google Authenticator, 1Password), base32 manual entry secret, 6-digit challenge code verification, and emergency recovery codes display.
   - Personal API Key Manager (`W4`): generate named keys, one-time reveal modal with copy button, list active keys with prefix/created dates, and instant revocation.

Production relational database migrations, persistent SQL ORMs, real third-party OAuth provider round-trips, multi-user group chat rooms, and audio/video calling are intentionally omitted to focus strictly on interaction ergonomics, social presence clarity, and 42 module compliance.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **Quiet Butler Workspace Harmony:** Does the slide-over Social Hub drawer keep the primary kanban board uncluttered and task-focused compared to persistent bottom-docked chat widgets?
- **Social Status & Presence Cluster:** Visual clarity and affordance of the global header pill: active persona avatar, connection indicator, unread message count badges, and online friend count.
- **Presence Indicators:** High-contrast, unambiguous visual states for friend status dots (`online` green, `away`/`busy` amber, `offline` muted gray).
- **1-to-1 Chat Stream Design:** Polish and readability of the chat interface: chronological message bubbles, clear sender/receiver distinction, timestamps, date dividers, unread indicators, and simulated typing animations.
- **Profile & Security Presentation:** Clean, cohesive presentation of the 42-specific profile components: avatar uploader, OAuth connection pill, interactive 2FA TOTP QR enrollment modal, and API key management table.

### 2. Procedural / Workflow Aspects
- **Context-Switching & Keystroke Efficiency:** Measuring the clicks and keystrokes required to check a friend's status, send a quick message, and return to an active kanban card. Keyboard navigation (e.g. `Esc` to close drawer, `Enter` to send message).
- **Friendship Request Lifecycle:** Testing the complete end-to-end friendship workflow: initiating a request, switching personas, reviewing pending requests, accepting/rejecting, and observing the immediate unlocking of chat.
- **Organization Colleague Discovery:** Evaluating the workflow of locating a coworker in a shared organization, viewing their shared spaces, and determining whether to send a friend request or initiate direct communication under both policy models.
- **Separation of Work vs. Social Conversations:** Flow of commenting on a task in the item drawer versus sending a private message in the Social Hub, ensuring zero friction when referencing work items.
- **2FA Enrollment & Recovery Flow:** The step-by-step UX of scanning a QR code, entering a TOTP token, and safely viewing/copying recovery codes.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **Client-Side State & Reactivity Architecture:** How cleanly Nuxt 4 `useState` or Pinia handles reactive in-memory collections of friendships, presence maps, active chat threads, and unread counters across persona switches without page reloads.
- **Slide-Over Drawer vs. Floating Dock Ergonomics:** Developer experience and CSS implementation complexity of a slide-over panel (using native dialog / transition components) versus draggable/docked floating chat windows, including focus trapping and DOM containment.
- **Client-Side TOTP & QR Code Generation:** Assessing the lightweight ergonomics of client-side QR generation (e.g. `qrcode` / SVG rendering) and TOTP token validation libraries in a browser environment without heavy backend round-trips.
- **Multi-Persona Simulation Architecture:** How effectively an in-memory event-bus pattern simulates concurrent WebSocket message delivery and presence changes for live 42 evaluation demonstrations.
