# run-502: First-Class Platform Records & Relational Data Access Layers (ORM vs. DAL vs. Raw Drivers)

**Kind:** exploration  
**Port:** 3502  
**DB:** postgres  
**Question:** Which candidate platform and social records (memberships, friendships, messages, comments, notifications, allocations, API keys) must be modeled as first-class relational tables in PostgreSQL versus embedded or deferred, and which data-access layer—a full ORM (W5), a type-safe query builder, or raw pg queries—provides the best balance of latency, type safety, SQL transparency, and developer ergonomics for C/C++ developers?

## Scenario

A developer with a systems and C/C++ background is architecting the relational database schema and data-access layer for Lerch. While the core domain invariants (`Space`, `Actor`, `Item`, `Hierarchy`) are well established, the system must accommodate platform, social, and integration records required by major modules:
- Space memberships and administrator roles (`U5`)
- Bilateral friendships, friend requests, and online presence (`U1`, `W3`)
- One-to-one private chat messages (`W3`)
- Chronological item discussions and comments
- In-app event-driven notifications (`W6`)
- Calendar time allocations linking items to users
- Public REST API keys with SHA-256 hashes, actor attribution, and rate-limit tracking (`W4`)

The developer opens the diagnostic workbench on port `3502` (`http://localhost:3502`) to evaluate two interconnected architectural questions:

1. **First-Class Platform Records:** Inspecting the proposed relational schema across 10 tables (`actors`, `spaces`, `memberships`, `items`, `friendships`, `messages`, `comments`, `notifications`, `allocations`, `api_keys`). The workbench displays foreign key graphs, cascade behaviors, and row counts, while explicitly contrasting these against candidate records that are deferred to buffer runs or embedded as JSON documents (`View`, `Template`, `Action`, `Meeting`, `Journal`).
2. **Data-Access Layer Tri-Mode Comparison:** Testing how relational queries are constructed and executed in Nitro server routes across three distinct architectural paradigms:
   - **Full Relational ORM (`W5`, e.g., Drizzle ORM / Prisma):** High-level declarative schema DSL, relation graphs, automated migrations, and abstracted query building.
   - **Type-Safe Query Builder / DAL (e.g., Kysely):** Pure SQL query construction with compile-time TypeScript type safety, zero code-generation runtime overhead, and explicit joins.
   - **Raw Driver (`pg`):** Direct parameterized SQL strings (`db.query('SELECT ...')`) with manual row mapping, providing zero abstraction overhead and complete SQL control.

The developer exercises four standard operational workflows spanning the platform entities:
1. *Item Context Read:* Fetching an item with its space details, author profile, attached comments, and linked artifact count.
2. *Social Feed & Inbox:* Querying a user's unread notifications and latest private messages from accepted friends.
3. *Security & Authorization Check:* Validating an incoming hashed `ApiKey`, checking rate-limit usage, and verifying space membership permissions in a single transaction.
4. *Batch Platform Mutation:* Creating an item comment, appending an audit notification event, and updating the item's `updated_at` timestamp within a transactional boundary.

For each workflow, the user toggles between the ORM, Query Builder, and Raw Driver implementations to inspect the generated SQL syntax, bound parameters, execution plan, and microsecond query latency side by side. A benchmark harness runs synthetic multi-query batches to measure throughput and memory pressure.

Full interactive chat interfaces, drag-and-drop kanban boards, live WebSocket transports, and multi-database MongoDB syncing are intentionally omitted to keep this prototype strictly focused on PostgreSQL relational modeling and Nitro data-access ergonomics.

## What to Evaluate

### 1. Visual & Presentation Aspects
- **Schema & ERD Inspector:** A clear, interactive entity-relationship viewer displaying the 10 relational tables, foreign key constraints, cascade rules (`ON DELETE CASCADE` vs `SET NULL`), unique indices, and column definitions.
- **SQL Transparency Inspector:** Side-by-side display showing the exact SQL statement produced by the ORM vs the Query Builder vs the handwritten raw `pg` query, highlighting SQL dialect variations, column aliasing, and join strategies.
- **Diagnostic Benchmark Dashboard:** A live comparative dashboard reporting execution metrics across all three data-access layers: P50/P95/P99 latency (ms), query execution plan (`EXPLAIN ANALYZE`) breakdown, and Node process heap allocation.

### 2. Procedural & Workflow Aspects
- **Mental Model Alignment for C/C++ Developers:** How intuitively each abstraction maps to systems concepts (memory layout, struct pointers vs foreign keys, explicit query execution vs hidden framework magic).
- **Error Traceability & Debugging Friction:** When schema mismatches or constraint violations occur, how clearly error messages identify the root cause across an ORM DSL, a query builder, and raw driver errors.
- **Schema Evolution & Migration Ergonomics:** Comparing declarative schema definition with automated migration generation against raw SQL DDL migration files in terms of maintainability, predictability, and container initialization speed.
- **Normalization vs Embedding Trade-Offs:** Evaluating whether platform records like `Notification` and `Comment` warrant independent first-class tables with relational integrity or whether any could be embedded as JSONB fields without degrading search and aggregation performance.

### 3. Technology & Stack Choices
- **Full ORM (`W5`, e.g., Drizzle ORM / Prisma):** Assessing developer experience, type inference fidelity without manual interfaces, cold-start penalty in Node containers, and whether the relational query API hides query complexity or introduces subtle N+1 query patterns.
- **Type-Safe Query Builder (Kysely):** Evaluating the balance between raw SQL transparency, compile-time query validation, zero runtime overhead, and ease of onboarding for developers accustomed to writing SQL directly.
- **Raw Driver (`pg`):** Measuring the baseline performance ceiling, connection pool behavior, and the engineering cost of manual type assertion and row transformation.
- **Module `W5` Selection:** Establishing an objective basis for selecting the production data-access layer that satisfies the `W5` subject requirement while maintaining clean ergonomics for the team.
