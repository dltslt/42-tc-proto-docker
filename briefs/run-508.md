# run-508: Multi-Field Search, Indexing & Privileged Pagination at Scale

**Kind:** benchmark  
**Port:** 3508  
**DB:** hybrid (PostgreSQL 16 Alpine + MongoDB 7)  
**Question:** How does multi-field full-text search, filtering, sorting, and pagination perform across PostgreSQL and MongoDB at 10k vs. 100k items while strictly enforcing multi-tenant space privileges, and how do PostgreSQL GIN/B-tree indexes compare to MongoDB compound and text/wildcard indexes on query latency, disk footprint, and cursor efficiency?

## Scenario

A developer or reviewer wants to evaluate how Lerch's search system handles real-world scale (10,000 to 100,000 items and 20,000 artifacts across 25 spaces) without sacrificing low latency (<50 ms) or leaking private data across space boundaries.

The user launches the prototype and selects an active actor persona (e.g., Alice who belongs to 3 organization spaces, Bob who has access only to his personal space, or Charlie who has access across 12 spaces). The application immediately updates its security scope: any subsequent query executed through the UI search view (satisfying **W11**) or the simulated public REST API (`GET /api/items`, satisfying **W4**) automatically enforces space boundary constraints at the database level.

The user explores the search experience across three operational dimensions:
1. **Multi-Field Filtering & Full-Text Search:** The user types search terms to match against item titles and descriptions, while applying arbitrary combinations of filters: space, state (`unstarted`, `started`, `done`, `discarded`), kanban column, tags, assigned contributor, and creation/schedule date ranges.
2. **Sorting & Deep Pagination:** The user sorts results by `title`, `created_at`, `scheduled_time`, or `effort`, and toggles between standard offset/limit pagination (page numbers, e.g. jumping to page 250) and keyset cursor-based pagination (next/previous opaque cursor tokens). This allows observing first-hand the performance degradation of deep SQL `OFFSET` vs. cursor lookups on a 100k dataset.
3. **Dual Storage Engine Benchmark & Query Plan Inspector:** The same dataset is mirrored in both PostgreSQL 16 and MongoDB 7. The user can toggle between engines or run queries in parallel to compare execution plans (`EXPLAIN ANALYZE` showing index scans vs. sequential scans in PostgreSQL, and `explain("executionStats")` showing `IXSCAN` vs. `COLLSCAN` in MongoDB), total query execution time (ms), and disk footprint of indexes.

Complex client-side graph visualizers, live WebSocket event synchronization (**W2**), collaborative rich text editing (**W7**), and binary file upload pipelines (**W12**) are intentionally omitted to keep this benchmark focused strictly on indexing, query planning, authorization boundaries, and pagination mechanics.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **Search & Filter Controls:** Ergonomics of combining free-text input with multi-select filter chips (`space`, `state`, `kanban`, `tags`, `contributor`, date ranges) without visual clutter.
- **Result Presentation & Match Highlighting:** Clear item and artifact card layouts displaying matched substrings, state badges, space ownership, tags, and attached artifact indicators.
- **Diagnostic Query Inspector:** An integrated, collapsible diagnostic drawer displaying real-time execution statistics: query response time (ms), database engine, raw SQL query or MongoDB aggregation pipeline, index used, rows examined vs. returned, and total index disk footprint.
- **Pagination UI Ergonomics:** Visual differences and user expectations between traditional numbered page navigation (offset) and forward/backward cursor navigation (keyset).

### 2. Procedural / Workflow Aspects
- **Space Access Boundary Enforcement:** Switching between actors immediately restricts the search space without manual filter configuration, verifying that unauthorized space items and artifacts never appear in results or total match counts.
- **Interactive Query Refining:** Procedural speed when adding, removing, and toggling compound filters to see whether response times remain sub-50 ms under varying selectivity (e.g., highly selective query matching 3 items vs. broad query matching 15,000 items).
- **Deep Pagination Cliffs:** Navigating to deep pages (e.g. page 1 vs. page 500) under offset pagination versus continuous keyset cursor traversal, exposing the latency cost of scanning through leading rows.
- **Public API Contract Parity:** Calling the backend API endpoint (`GET /api/items`) with identical query and cursor parameters, validating that the public API shares the exact same filter, index, and pagination semantics as the in-app search UI.

### 3. Technology / Stack Choices
- **PostgreSQL Indexing Strategies:** Comparing full-text search indexes (`tsvector` + GIN) vs. trigram indexes (`pg_trgm` + GIN/GiST) for partial keyword matches, combined with composite B-tree indexes for `(space_id, state, created_at)`.
- **MongoDB Indexing Strategies:** Evaluating text indexes (`$text`) vs. compound wildcard and multikey array indexes (for `tags` and `contributors`), measuring index memory footprint and cache retention.
- **Keyset vs. Offset Pagination:** Ergonomics and implementation complexity of multi-column keyset cursors (`(sort_value, id)`) in both relational SQL and MongoDB aggregation vs. naive offset queries.
- **Database Engine Suitability at Scale:** Evaluating whether a hybrid approach (storing spaces in PostgreSQL and items in MongoDB, or running full-text search natively in PostgreSQL) provides sufficient speed and operational simplicity at 100k items, or whether an external dedicated search engine (e.g., Elasticsearch / Meilisearch) would be warranted in production.
