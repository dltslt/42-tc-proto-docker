# Brief: run-103 — Two views on one contract

## Scenario

Run 102 built a versioned `/api/v1` and froze it. Its tests were written by the same author as the
API, so they cannot show whether the API suits a real client. This run is the first honest client:
a small web UI that knows the API only from its published OpenAPI document. The question this run answers:

> Can two different views, a list and a board, be built on the frozen `/api/v1` of run-102 with
> no change to run-102, and where does the contract make a screen awkward?

The deliverable is as much the **findings** as the UI. Every place where the contract makes
a screen slow, clumsy or impossible is written down. Nothing is fixed by editing run-102.

## Stack

- `DB=none`, started from `prototypes/template/`. No code is copied from other runs.
- Nuxt 4 and Nitro, plain Vue components, Tailwind / CSS. No UI library.
- The run has no database and no business rules. All data and all rules come from run-102.
- Types for requests and responses are written by hand from the OpenAPI document, or generated from it. Nothing is imported from `prototypes/run-102/`.

## Ground rules

- **Read the contract, not the code.** The only source of truth about run-102 is its running
  `GET /api/v1/openapi.json`, plus the shared specs. Do not open, search or diff `prototypes/run-102/`.
- **run-102 is not edited.** If the API cannot do what a screen needs, record a finding and work around it in the client, or cut the feature.
- **A workaround is a finding.** Several requests combined into one screen, a join done in the browser, or polling count as findings.
- **One client, one place.** All API calls go through one small module (`app/api.ts` or similar). Components never call `fetch` themselves.

## How it reaches run-102

run-102 sends no CORS headers, and a browser page at `localhost:3103` cannot call `localhost:3102` directly.
So this run proxies:

- Nitro forwards `/api/v1/**` to run-102 (a `routeRules` proxy, or one catch-all server route). Inside the Docker network the target is `http://run-102:3102`; the target comes from an environment variable.
- The browser only ever talks to its own origin. The proxy adds nothing and changes nothing.
- Orientation comments explain the hop: browser → this Nitro server → run-102 container.

If run-102 is not running, the UI shows a clear message instead of a blank page.

## Identity

- A "current user" selector in the header lists actors from `GET /actors` and sends the chosen id as `X-Actor-Id` on every call.
- The choice is kept in a cookie (`useCookie`), so server-side rendering and the browser agree.
- A space selector lists `GET /spaces` for the current actor. Switching actor resets the space.

## Seeded data

`make seed RUN=102` gives the UI this data to work with. It is visible through the API, so nothing here
needs a look at run-102's code. Names and counts are as seeded today; check them against the live API.

- **Actors:** Ada, Ben and Cleo (humans) and Lurch (an agent).
- **Spaces:** one personal space each for Ada, Ben and Cleo; **Dinner party** (members Ada, Ben, Lurch) and **Studio** (member Cleo). Lurch has no personal space.
- **Columns:** every space has the same four, Backlog, In progress, Done, Discarded, one per state.
- **Dinner party** is the main test space: 11 items, three levels deep (project "Host the dinner" → story "Plan the menu" → tasks), items in all four states, some with a lead and some without.
- **Tags:** in Dinner party `urgent`, `shopping`, `kitchen`; in Studio `launch`. Six items carry a tag, and one item carries `urgent` while its parent carries it too.
- The other spaces hold a handful of items each: enough to test the space switcher and isolation (for example, Ada must not see Studio).

The seed is the starting point, not a fixture to protect. The UI may change this data; re-seeding does not undo
changes, so note any state a test depends on.

## The two views

Both views show the same space and the same items. Switching between them keeps the current space and actor.

**List view** (route `/list`)
- The item hierarchy as a tree by `parent_id`, siblings in `position` order, children collapsible.
- Each row: type, title, state, lead name, tags.
- Create an item (title alone is enough, optionally under a selected parent), edit the title, delete (asks `subtree` or `lift` when the item has children).

**Board view** (route `/board`)
- One column per space column, in board order, items inside each in `position` order.
- Move a card to another column or to a place among its siblings by drag and drop, with a button fallback ("move to ...").
- Create an item straight into a column (title alone is enough).

**Both views**
- Tags: show them, add and remove them on an item.
- A conflict on edit (409) shows the stored version next to the user's text and lets them choose.
- A change made in one view appears in the other without a manual reload (see "Staying current").

## Staying current

The API has no push channel. Use the event log as designed: remember the last event id seen in the
space and poll `GET /spaces/:id/events?after=<id>`. When new events arrive, refetch only what they name.
Record how well this works (delay, number of requests, anything that needs a full refetch).

## Findings to collect

Keep a running list in `docs/run-103/NOTES.md` under "Open questions touched". For each finding write
what the screen needed, what the contract offered, and the workaround. Look especially at:

- **Request count:** how many calls one screen load takes for the list view and for the board view. Responses hold ids only (`?include=` is not built), so names of leads and tags need extra calls or a client-side join.
- **Board loading:** one call per column, or one big list sorted by position and grouped in the browser. Which is simpler, and which breaks past the page limit of 200?
- **Tree loading:** can the full hierarchy be fetched in one pass, or does it take a call per level?
- **Filtering:** what cannot be filtered that a screen wants (for example by tag).
- **Moves:** is `after_id` / `before_id` enough for drag and drop? What happens when two users drop on the same gap?
- **Conflicts:** is the 409 body (`error.current`) enough to build a merge dialog?
- **Errors:** does the shared error shape (`code`, `message`, `fields`) map cleanly to form messages?
- **Live updates:** how polling the event log behaves, and what the `changes` payload does or does not tell the client.
- **Anything in the OpenAPI document that was wrong, vague or missing** compared with real behaviour.

## Out of scope

Login, roles, real-time transport, drag-and-drop between spaces, bulk edits, offline use, mobile layout,
accessibility audits, tests of run-102 itself, and any change to run-102 or to the frozen contract.
Styling is plain and only has to be readable.

## Done when

1. `make up RUN=103` starts the UI at `http://localhost:3103`, with run-102 running and seeded. `make seed` is not needed (no database).
2. The header actor selector lists the actors from the API, and every API call after it carries `X-Actor-Id`. A non-member never sees another space's items.
3. The list view shows the seeded hierarchy as a tree in `position` order, with each item's lead name and tags.
4. The board view shows every column of the space in board order with its items in `position` order, and the same items appear in both views.
5. Creating an item from a title alone works in both views, and the item lands in the first `unstarted` column.
6. A drag-and-drop move on the board (or its button fallback) changes column and place, survives a reload, and shows as a move in the other view.
7. Editing a title in two browser windows on the same item shows a conflict dialog in the second window, built from `error.current`.
8. Deleting an item with children asks for `subtree` or `lift` and leaves a consistent tree.
9. Adding and removing a tag shows in both views.
10. A change made in one browser window appears in a second window within a few seconds, through the event log only.
11. With run-102 stopped, every page shows a readable error instead of crashing or going blank.
12. `git diff` for the run shows no change to `prototypes/run-102/`, `contract/` or any run-102 test, and the run-102 test suite still passes.
13. `docs/run-103/NOTES.md` lists the findings above, each with a one-line recommendation: **fix in a new additive endpoint or field**, **fine as it is**, or **needs a decision**.
