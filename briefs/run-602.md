# run-602: The Lerch Shell, Zoom Engine (Registerkarten) & "Next Relevant Work" Hub

**Kind:** interaction-lab  
**Port:** 3602  
**DB:** none  
**Question:** How does an application shell built around physical notebook edge tabs (*Registerkarten*), progressive field disclosure, and a global keyboard command palette reduce navigation friction compared to traditional web routing across 1 to 5 hierarchy levels, and which deterministic prioritization heuristic best computes the "Next Relevant Work" for a user?

## Scenario

A developer with a systems and C/C++ background is evaluating the frontend user experience and shell architecture for Lerch. In conventional web project management tools, drilling down through a hierarchical work breakdown structure (`Space` $\to$ `Project` $\to$ `Epic` $\to$ `Story` $\to$ `Task` $\to$ `Subtask`) relies on browser URL page routing (e.g. `/spaces/1/projects/5/epics/12/tasks/88`). This causes page reload flashes, loss of spatial context, and visual clutter—either by overwhelming high-level views with leaf-task details or hiding leaf-task progress behind deep, isolated page hops. Furthermore, users often suffer from "what do I work on next?" paralysis when viewing sprawling work trees.

The developer launches the prototype on port `3602` (`http://localhost:3602`) to explore a spatial notebook interface that remains lightweight for small uses while gracefully scaling to multi-level enterprise trees:

1. **Agnostic Core Across Scale Datasets (`§1.4 Q2`, `§1.4 Q3`):** The developer can toggle between two pre-seeded in-memory datasets using a header control:
   - *Dataset A (Minimal Scale — 10-Item Personal List):* A flat or 1-level weekend task list. Demonstrates that the shell stays out of the way—no unnecessary tabs, no overwhelming epic/story rollups, functioning like a tactile, quiet scratchpad.
   - *Dataset B (Enterprise Scale — 5-Level Engineering Tree):* A 5-level deep work breakdown tree (`Space` $\to$ `Project` $\to$ `Epic` $\to$ `Story` $\to$ `Task` $\to$ `Subtask`) with over 100 items, multiple contributors, blocker dependencies, effort allocations, and attached artifacts.

2. **Notebook Edge Tabs (*Registerkarten*) & Spatial Zoom Engine:**
   - Physical tab labels mounted along the container edge represent active zoom depth (`Space`, `Project`, `Epic`, `Story`, `Task`, `Subtask`).
   - Clicking an edge tab or pressing zoom navigation keys (`[` and `]`, or number keys `1`–`5`) smoothly transitions the zoom depth in place without URL page reloads or layout disorientation.
   - An interactive ancestry trail (breadcrumbs with parent context) maintains spatial orientation and enables 1-click jumps back to any ancestor node.

3. **Progressive Field Disclosure (`§1.3`, `§1.4 Q3`):**
   - *High-Level Overview Depth (`Space` / `Project` / `Epic`):* Suppresses granular leaf fields (long descriptions, minute-level `scheduled_time` slots, individual checklists, raw artifact files). Instead, surfaces aggregate rollup indicators: total estimated `effort` sum, completion percentage bars, and count of open blocker dependencies.
   - *Leaf Depth (`Task` / `Subtask`):* Unfolds fine-grained operational fields: direct `effort` estimate (hours/points), `scheduled_time` slot, interactive checklist, blocker severity badges, and attached artifact links.

4. **Global Keyboard Command Palette (`Cmd+K` / `Ctrl+P`):**
   - Instant keyboard-driven palette with fuzzy search across all items in the workspace regardless of current zoom depth.
   - Fast 1-step actions: jumping to any item or zoom layer, mutating item state (`unstarted`, `started`, `done`), creating child subtasks, or setting an item as the active focus.

5. **"Next Relevant Work" Hub (The Butler Panel, `§1.4 Q1`):**
   - A dedicated focus panel embodying Lerch the quiet butler, surfacing the single next actionable item for the user.
   - To resolve `§1.4 Q1` without relying on an opaque machine-learning model, the interface allows toggling between candidate deterministic prioritization heuristics:
     - *Policy 1 (In-Progress & Schedule Recency):* Prioritizes items already `started` by the active actor, sorted by today's `scheduled_time` slot, then highest priority, then unblocked status.
     - *Policy 2 (Critical Blocker Clearance):* Prioritizes unblocked items whose completion unblocks the highest number of downstream items or resolves high-severity blockers (`cannot do anything`), maximizing team velocity.
     - *Policy 3 (Quick-Win & 1-Day Sizing Hygiene):* Prioritizes unblocked `unstarted` leaf tasks scheduled for today with `effort <= 1 day`, encouraging forward momentum and reinforcing 1-day task sizing hygiene (`§2.1 Q3`).
     - *Policy 4 (Configurable Weighted Vector):* An interactive slider matrix balancing schedule urgency, blocker impact, and item state.
   - Each recommendation displays a visible, inspectable "Explanation Trail" (e.g. *"Why this item? In-progress · Scheduled for 14:00 · Unblocks 2 team tasks"*), making the selection transparent.

Persistent backend database engines (PostgreSQL/MongoDB), WebSocket transports, user authentication flows, file uploads to disk, and full multi-column Kanban boards are intentionally omitted (`DB=none`) to keep the prototype strictly focused on client-side spatial navigation, keyboard ergonomics, progressive disclosure, and the next-work prioritization algorithm.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **Notebook Edge Tabs (*Registerkarten*) Tactile Aesthetic:** Does the physical tab metaphor provide an intuitive spatial sense of notebook depth compared to traditional web page breadcrumbs and sidebar menus?
- **Progressive Disclosure Clarity:** Does hiding granular operational fields at overview zoom levels eliminate visual noise while preserving high-level situational awareness? Are rollup metrics (effort sums, progress bars, blocker counts) immediately legible?
- **"Next Up" Butler Card & Explanation Trail:** Does the butler focus card feel calm, clean, and helpful? Does the transparent explanation trail make algorithmic item selection trustworthy and understandable at a glance?
- **Scale Contrast (Minimal vs. Deep Enterprise):** Comparing the presentation of the 10-item personal list against the 5-level 100+ item engineering tree. Does the agnostic shell remain unobtrusive when work is simple, while scaling cleanly without visual collapse when work is complex?

### 2. Procedural / Workflow Aspects
- **Navigation Efficiency & Context Retention:** Measuring clicks and keystrokes required to navigate from the root Space down to a leaf Subtask and back. Does spatial in-place zooming preserve mental context better than standard browser back/forward routing?
- **Keyboard-First Navigation (`Cmd+K` / `Ctrl+P`):** Speed and ergonomics of using the command palette to search items across depths and execute 1-step actions without reaching for the mouse.
- **"Next Relevant Work" Heuristic Evaluation (`§1.4 Q1`):** Comparing the practical utility of the prioritization policies. Does the Blocker Clearance policy surface genuinely critical team work, or does the In-Progress / Schedule Recency policy feel more natural for an individual contributor?
- **1-Step Action Friction:** Ease of capturing a child task or changing an item's state directly from the command palette or zoom view in minimal interactions.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **Vue 3 Spatial Transitions & Reactivity:** How cleanly does Vue 3's Composition API (`ref`, `computed`, reactive tree stores) manage recursive hierarchy traversals and rollups? Do zoom transitions maintain 60fps responsiveness without DOM layout thrashing?
- **Command Palette Implementation:** Evaluating a custom lightweight Vue component using the HTML `<dialog>` element / popover API versus third-party command palette libraries in terms of keyboard listener hygiene, focus management, and bundle footprint.
- **Deterministic Prioritization Engine:** Evaluating the clarity and maintainability of functional TypeScript ranking pipelines for systems developers learning web architectures.
- **In-Memory Tree Traversal Ergonomics:** How easily can C/C++ developers follow the data structure (recursive parent-child item maps vs. flat indexed item dictionaries) in a client-side TypeScript application.
