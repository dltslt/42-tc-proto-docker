# run-600: Progressive Item Creation, Lifecycle States & Kanban Sizing Lab

**Kind:** interaction-lab  
**Port:** 3600  
**DB:** none  
**Question:** How do fast keyboard capture syntax, distinct `new` inbox vs. column-less `unstarted` states, soft sizing hygiene prompts (>1 day effort) vs. hard gates, and Definition of Ready/Done workflows affect keystroke efficiency, cognitive load, and board predictability across an item's full lifecycle?

## Scenario

A team of developers with a C/C++ systems background is designing the core frontend interaction layer for Lerch. They must balance two competing core values: the "fewest steps rule" (§1.3), where turning a raw thought into a tracked item takes the absolute minimum effort, and rigorous task hygiene (§2.1), where items larger than one day break down into manageable child tasks before clogging execution boards.

The developer launches the prototype on port 3600 (`DB=none`, running in-memory with pre-seeded JSON fixtures) and enters an interactive laboratory designed to compare competing lifecycle models, capture techniques, and board policies side by side.

Through the prototype interface, the developer explores four key interaction areas:

1. **Progressive Quick Capture vs. Structured Modal Creation:**
   - *Inline Shorthand Capture:* A persistent single-line input bar accessible via global keyboard shortcut (`/` or `Ctrl+K`). The user types raw input using lightweight token shorthand: `Refactor network buffer pool #infra #networking @mw !critical ~6h`. The parser provides live inline chip tokenization as characters are typed. Hitting `Enter` commits the item in a single action, creating a valid item with title, tags, contributor, blocker severity, and effort estimate.
   - *Structured Modal Dialog:* A traditional form with discrete form controls (text field, dropdown pickers, date/time inputs, tag combobox).
   - *Interaction Telemetry HUD:* A live HUD counter displays exact keystroke counts, mouse click counts, and elapsed input duration (seconds) per created item, providing hard empirical data on input efficiency.

2. **Triage Invariant Comparison (`§2.1 Q1`):**
   The developer toggles between two competing domain lifecycle models to determine how newly captured items enter the system:
   - *Model A (Dedicated `new` State):* Items enter with `state: "new"` and sit in a dedicated "Inbox / Triage Tray" isolated from the board. Items cannot move to active kanban columns or be scheduled until an explicit triage action promotes them to `unstarted`.
   - *Model B (Column-less `unstarted` Baseline):* Items strictly adhere to the 4 invariant lifecycle states (`unstarted`, `started`, `done`, `discarded`). Un-triaged items enter as `unstarted` with `column: null` and appear in a collapsible "Backlog / Unassigned" drawer beside the board. Triage is simply dragging or assigning an item to a column.
   The developer tests creating and triaging 10 test items in each model to evaluate whether an explicit `new` state prevents board clutter or adds unnecessary state machine friction.

3. **Sizing Hygiene & 1-Day Effort Breakdown (`§2.1 Q3`):**
   The developer explores the practical application of the domain rule: *"something you cannot finish in a day is not a task"*.
   - When an item's estimated `effort` exceeds 1 working day (>8 hours or >1d), the card visually flags the threshold with a high-contrast sizing warning chip.
   - The developer tests an *Inline Breakdown Assistant*: a 1-click decomposition drawer that lets the user quickly carve the oversized item into smaller child subtasks (e.g., splitting a 16h task into two 6h and one 4h subtask).
   - The interface tests upgrading the item's scale type from `task` to `story` or `epic` with child hierarchy relations, dynamically rolling up child effort to the parent while clearing the sizing warning.

4. **Kanban Movement, Gates & Definition of Ready / Done (`§2.1 Q2`, `§2.1 Q4`, `§2.1 Q5`):**
   The developer tests items moving across default columns (`backlog`, `in progress`, `done`) and custom workflow columns (`design`, `build`, `qa`).
   - *Gate Policy Toggle:* The developer switches between *Soft Advisory Mode* (items can be dragged freely; unmet conditions surface subtle warning badges without blocking) and *Hard Gate Mode* (dragging into `in progress` or `done` is blocked until Definition of Ready [DoR] or Definition of Done [DoD] checklist criteria are satisfied).
   - *Checklist Architecture:* Evaluates whether DoR and DoD work best as simple per-item markdown checklists or space-level templates automatically inherited by new items.
   - *Lifecycle Extensions (`§2.1 Q4`):* Tests one-click board archival (moving completed or discarded items to an off-board archive drawer with instant restore) and the "reviews-as-fresh-items" workflow (clicking "Request Review" spawns a linked child review item assigned to a peer instead of forcing an artificial "In Review" board column).

Persistent database engines, multi-user WebSockets, OAuth authentication, and external file uploads are intentionally omitted to keep this prototype strictly focused on client-side reactivity, keyboard mechanics, and lifecycle state ergonomics.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **Inline Shorthand Tokenizer:** Visual clarity of live syntax highlighting and interactive chip preview (tags, assignees, effort, severity) rendered directly inside or below the single-line capture bar as the user types.
- **Sizing Hygiene Prompts:** Visual salience of task sizing indicators (>1 day / >8h) on kanban cards; comparing subtle warning dots, colored badges, and collapsible decomposition prompts.
- **Intrinsic State vs. Visual Column Representation:** Visual distinction between an item's underlying domain `state` (`unstarted`, `started`, `done`, `discarded`) and its current visual `column` (`backlog`, `design`, `build`, `qa`, `done`).
- **Telemetry & Interaction HUD:** A persistent diagnostic header/overlay showing real-time interaction metrics (keystrokes, clicks, input duration) and comparison summaries.

### 2. Procedural / Workflow Aspects
- **Fewest Steps Efficiency:** Quantifiable comparison of creating items via shorthand keyboard capture versus multi-step modal dialogs, measuring cognitive friction and input speed.
- **Triage Model Friction (`§2.1 Q1`):** User experience of triaging new thoughts: does a distinct `new` inbox state clarify the boundary between ideation and planning, or does a column-less `unstarted` drawer feel simpler and more natural?
- **Column Gating vs. Flow Velocity (`§2.1 Q2`):** Procedural impact of hard blocking gates versus soft advisory warnings when transitioning cards across column boundaries.
- **Decomposition Experience (`§2.1 Q3`):** The operational ease of breaking down an oversized task into child subtasks inline without navigating away from the active board view.
- **Review Workflow (`§2.1 Q4`):** Experience of handling reviews as newly spawned linked items rather than board columns or lifecycle states.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **Nuxt/Vue Client Reactivity:** Developer experience using Vue 3 reactive primitives (`ref`, `computed`, `reactive`) for instant local board manipulation without backend round-trips.
- **Zero-Dependency Micro-Parser:** Feasibility and DX of authoring a lightweight tokenizing parser for shorthand capture (`#`, `@`, `!`, `~`) in pure TypeScript versus pulling in heavy third-party parsing dependencies.
- **Keyboard Shortcut Management:** Ergonomics of handling global and scoped keyboard listeners (`Cmd+K`, `/`, `Enter`, `Escape`, `Tab`) cleanly within Vue `<script setup>` without DOM event leakage.
- **Drag-and-Drop Implementation:** Evaluating client-side drag-and-drop mechanics (HTML5 Drag and Drop API vs. lightweight Vue composables) for card repositioning, column movement, and gate validation.
