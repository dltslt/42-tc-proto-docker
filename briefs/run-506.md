# run-506: Real-Time Collaborative Description Editing & Field Locking Protocols

**Kind:** exploration  
**Port:** 3506  
**DB:** postgres  
**Question:** How do live typing in item descriptions and edit locking combine when multiple users edit the same item at once, and when should changes be persisted to PostgreSQL versus held in memory?  

## Scenario

Two developers on a team—Alice and Bob—open the same task item simultaneously. Alice begins refining the description while Bob intends to adjust its effort estimate and move its kanban state. Without coordination, concurrent edits cause race conditions, lost updates, or confusion over who is changing what.

In this prototype, the developer evaluates two distinct real-time synchronization protocols for collaborative item editing:

1. **Protocol A (Pessimistic Field Lease + Live Keystroke Preview):**
   - Taking focus on `description` (or any editable field) immediately requests a short-TTL lease (e.g., 5–10 seconds) from the Nitro server over WebSockets.
   - The active holder's keystrokes are broadcast in real time to all other connected clients as a live preview ("Alice is typing...").
   - To other users, the field appears visually locked with the holder's avatar, name, and lease countdown timer. Attempting to edit is prevented, with the option to queue a local draft.
   - The lease is continuously renewed via typing heartbeats and automatically released on blur, explicit save, or after TTL expiration if the browser disconnects or crashes.
   - Keystrokes are buffered in server memory and flushed to PostgreSQL only upon blur, explicit save, or lease release.

2. **Protocol B (Optimistic CRDT / Lock-Free Text + Discrete Field Locking):**
   - The `description` field supports lock-free concurrent editing: Alice and Bob can type simultaneously at different positions in the text. Edits and cursor positions merge without conflict using an in-memory document model (such as Yjs or an operational text merge).
   - Discrete selector fields (`state`, `kanban` column, `effort`, `score`) maintain exclusive field leases, as discrete enumerations cannot be merged character-by-character without corrupting domain state.
   - Text updates stream continuously in memory across connected clients, with debounced batch persistence to PostgreSQL occurring after typing pauses or explicitly triggered save points.

The prototype provides a dual-actor workbench (allowing side-by-side or multi-tab testing as Alice and Bob), an interactive protocol toggle to switch between Protocol A and Protocol B on the fly, and a diagnostic telemetry HUD. The HUD exposes active in-memory leases, WebSocket message traffic, connection drop simulations, and a live comparison of Nitro in-memory state versus committed PostgreSQL table rows.

Full user authentication, complex RBAC, file artifact uploads, and large kanban boards are intentionally omitted to keep the prototype strictly focused on synchronization mechanics, lock lifecycles, and write persistence boundaries.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **Lock Ownership & Presence Signaling:** How clearly does the interface communicate who holds an active field lease (e.g., colored borders, avatar tags, remaining lease countdown, "Locked by Alice")?
- **Live Preview vs. Multi-Cursor Rendering:** Comparing the visual clarity and distraction level of a read-only live keystroke preview (Protocol A) versus dual real-time collaborative cursors (Protocol B).
- **Contention & Lockout Feedback:** How intuitively the UI indicates that a field cannot be edited without jarring the user or silently discarding keystrokes.
- **Diagnostic Telemetry HUD:** Visual presentation of real-time server metrics (active room clients, in-memory lease table, WebSocket frame counters, and memory vs. database persistence diffs).

### 2. Procedural / Workflow Aspects
- **Lease Acquisition & Release Lifecycle:** The feel of acquiring a lock on focus, renewing it invisibly while typing, and releasing it on blur or explicit submit.
- **Disconnection & Orphan-Lock Recovery:** How the system handles abrupt browser closing, tab crashes, or network loss—verifying that locks auto-expire via TTL without permanently wedging the field.
- **Local Draft Queueing:** If a user attempts to edit a locked field, evaluating the friction and usability of maintaining a local uncommitted draft versus blocking input entirely.
- **Granular vs. Whole-Item Locking:** The procedural ergonomics of locking individual fields (allowing Bob to change `effort` while Alice edits `description`) versus locking the entire item record.

### 3. Technology / Stack Choices
- **Nitro WebSocket Architecture (`crossws`):** Ergonomics and developer experience of building per-item pub/sub rooms, presence tracking, and heartbeat timers directly within Nuxt 4 / Nitro server handlers.
- **Pessimistic Lease vs. CRDT Complexity:** Comparing the implementation complexity, bundle footprint, and mental model of a server-enforced mutex protocol versus a client-side CRDT library for a team with a C/C++ background defending at a 42 evaluation.
- **Persistence Boundaries & Write Amplification:** Demonstrating why streaming 60 keystrokes/second directly into PostgreSQL SQL `UPDATE` queries causes write amplification and row-lock contention, versus buffering active state in Nitro memory and flushing on blur or idle debounces.
- **Fault Resilience & Edge Cases:** How reliably each protocol recovers from packet loss, simulated 500ms network jitter, and race conditions when two users click into a field within milliseconds of each other.
