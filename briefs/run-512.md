# run-512: Volume File Storage, Space-Scoped Asset Streaming & Auth Extensions

**Kind:** exploration  
**Port:** 3512  
**DB:** postgres  
**Question:** How should container-volume file storage and space-scoped asset streaming (W12) be structured to prevent unauthorized asset leakage, and what schema extensions, cryptographic storage patterns, and account-linking rules are required on Actor and Artifact to support standard authentication (U1), 42 OAuth 2.0 (U3), and TOTP 2FA (U6)?

## Scenario

A team of developers with a C/C++ systems background is designing the boundary where the web application interacts with the physical filesystem, container isolation, and external identity providers. In systems programming, files are frequently written to disk or memory-mapped directly, while POSIX permissions (`chmod`/`chown`) enforce file access. In modern web architectures, files uploaded to a team collaboration platform (such as Lerch) cannot simply be placed into a public web root (e.g. `/public` or static file server), because an artifact attached to an item in a private organization space (`§2.8`) must never leak to unauthenticated users or members of other spaces.

Furthermore, user accounts (`Actor`, `§2.8`) require robust authentication mechanisms that go beyond simple seeded records: password authentication (`U1`), federated OAuth 2.0 sign-in with 42 (`U3`), and Time-based One-Time Password (TOTP) two-factor authentication with recovery codes (`U6`). Systems developers must confront how cryptographic keys, shared secrets, and third-party identities are stored and validated. Unlike passwords (which are one-way hashed with algorithms like Argon2 or bcrypt), TOTP shared secrets must be recoverable by the server to compute the RFC 6238 HMAC-SHA1 verification window, requiring symmetric encryption at rest, while single-use recovery codes must be stored as one-way hashes.

The developer launches the diagnostic workbench on port `3512` (`http://localhost:3512`) running against PostgreSQL 16 Alpine and a dedicated Docker volume (`lerch_uploads`). The workbench allows the developer to test and evaluate three core subsystems:

1. **Volume File Storage & Space-Scoped Asset Streaming (`W12`):**
   - **Upload & Validation:** The developer uploads files of various types (images, PDF documents, text logs) both as item artifacts (`kind: "file"`) and user avatars (`U1`). The system performs client-side inspection and server-side verification: enforcing maximum payload limits (e.g., 2 MB for avatars, 10 MB for artifacts) and inspecting magic bytes (file signatures) to detect spoofed MIME types (e.g. an executable or HTML file renamed to `.png`).
   - **Volume Persistence:** Files are streamed directly into an isolated Docker volume directory (`/data/uploads`) using a deterministic, collision-free storage layout (such as space-partitioned directories or content-addressable SHA-256 hashes). No file binaries are stored as SQL BLOBs in PostgreSQL.
   - **Space-Scoped Protected Streaming:** Files are served exclusively through an authenticated Nitro endpoint (`GET /api/spaces/:space_id/artifacts/:id/download` or `/stream`). The developer switches active personas (Space Admin, Space Member, Outside User, Unauthenticated) to verify that the server checks `can(actor, "read", space)` before streaming the file. The endpoint sets strict defensive HTTP headers (`Content-Disposition`, `Content-Type`, `X-Content-Type-Options: nosniff`).
   - **Lifecycle & Orphan Deletion:** Deleting an artifact removes its database metadata and unlinks the underlying file from the Docker volume, preventing orphaned disk leaks.

2. **OAuth 2.0 Remote Authentication & Email-Based Account Linking (`U3`):**
   - The developer tests the 42 OAuth 2.0 Authorization Code flow. To enable fully autonomous, offline evaluation inside Docker without requiring external network access, the prototype provides a toggle between a local Mock 42 OAuth Provider (running in the container) and a live 42 API endpoint.
   - The developer evaluates account-linking behavior (`§2.8`):
     - *Existing User Linking:* When an existing email/password user logs in via 42 OAuth and the 42 profile email matches the existing account, the system securely attaches the OAuth provider record (`provider: "42"`, `provider_user_id`) to the existing `Actor` without resetting or overwriting the existing password hash.
     - *New User Provisioning:* When a previously unknown user signs in via OAuth, a new `Actor` record is created, their avatar is fetched or set to default, and their default personal space (`§2.8`) is automatically initialized.
     - *Dual-Method Authentication:* The user demonstrates that they can subsequently log in using either their original password or 42 OAuth.

3. **Complete Two-Factor Authentication & Recovery Codes (`U6`):**
   - **TOTP Enrollment:** A user initiates 2FA setup. The server generates a cryptographically secure Base32 secret and an `otpauth://totp/...` URI rendered as a QR code and raw textual secret. The user must provide a valid 6-digit TOTP code matching the current time window before 2FA is officially marked active.
   - **Cryptographic Storage:** The developer inspects how credentials are stored in PostgreSQL. The prototype demonstrates storing the TOTP secret encrypted at rest using AES-256-GCM (with an environment key) rather than plaintext, while 8–10 single-use recovery codes are stored as hashed strings (bcrypt/SHA-256).
   - **Two-Step Login Challenge:** When 2FA is active, standard password or OAuth login yields a temporary, restricted two-factor challenge token (`2fa_pending`). The user must present a valid time-stepped code (with ±1 step / 30-second clock-drift tolerance) or burn a recovery code to receive a full authenticated session. Once a recovery code is used, it is immediately invalidated in the database.

Full drag-and-drop Kanban boards, real-time WebSocket cursor synchronization, email SMTP servers, and multi-tenant billing are intentionally omitted to keep this prototype strictly focused on container volume file I/O, security middleware, and authentication credential storage.

## What to Evaluate

### 1. Visual / Presentation Aspects (Diagnostic Tooling)
- **Volume & Storage Explorer:** A diagnostic view displaying physical files on the Docker volume (`/data/uploads`), showing file path, byte size, detected MIME type, SHA-256 hash, and associated database record (`Actor.avatar` or `Artifact.id`).
- **Space Permission Matrix & Access Simulator:** An interactive panel with an active persona switcher (e.g. Alice: Admin of Org Space A; Bob: Member of Org Space A; Charlie: User in Space B only; Anonymous Guest). When any persona attempts to stream or download a file artifact, the interface visually displays the resulting HTTP status code (`200 OK`, `401 Unauthorized`, `403 Forbidden`) and header configuration.
- **File Preview & Upload Experience:** Clear visual feedback for file uploads: client-side progress indicators, drag-and-drop file target, instant image previews for avatars and graphics, and structured metadata chips for documents (file size, MIME type, upload timestamp).
- **Security & Identity Status Card:** A user profile diagnostic card displaying authentication state: local password status, linked OAuth identity (provider, remote user ID, linked email), 2FA status badge (`Enabled` / `Disabled`), remaining recovery codes count, and a TOTP QR code generator.

### 2. Procedural / Workflow Aspects
- **Multipart Streaming & Validation Ergonomics:** Experience of handling multipart/form-data uploads in Nuxt/Nitro. Verifying how streaming directly to disk avoids buffering large files in Node.js process heap memory, and evaluating the error experience when magic-byte validation rejects an invalid file.
- **Space-Scoped Streaming vs. Public Assets:** Experiencing the architectural and latency difference between static asset serving (`/public`) and authenticated stream pipelines (`createReadStream` piped via Nitro response), confirming that no unauthenticated URL or path traversal trick (`../../`) can access private artifacts.
- **Account Linking & Identity Conflict Resolution:** Testing the operational flow when signing in with OAuth: matching emails, mismatched emails, and verifying that unlinking an OAuth provider or resetting a password preserves user data and space memberships.
- **2FA Challenge & Recovery Protocol:** Experiencing the two-step login lifecycle: issuing ephemeral challenge sessions, validating TOTP codes against Unix epoch time steps, handling clock drift (±30 seconds), and burning single-use recovery codes.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **File Streaming in Nitro (h3):** Evaluating Nitro's file upload parsing (`readMultipartFormData` vs. Node stream consumers like `busboy`) and streaming responses (`sendStream`) within container boundaries.
- **Docker Named Volumes & Filesystem Permissions:** Assessing container volume configuration (`lerch_uploads`), Linux UID/GID file permission compatibility between container processes and host mounts, and volume retention across container restarts.
- **MIME Sniffing & Magic Bytes:** Selecting a lightweight, dependable magic-byte detection tool (e.g. `file-type` or native byte buffer inspection) to prevent malicious file uploads.
- **Cryptographic Storage Patterns on `Actor` & `Artifact`:**
  - Deciding whether to normalize auth credentials into separate tables (`actor_credentials`, `oauth_accounts`, `actor_recovery_codes`) or store structured fields on `Actor`.
  - Evaluating AES-256-GCM symmetric encryption for TOTP secrets vs. one-way hashing for recovery codes and passwords.
  - Evaluating TOTP libraries (e.g., `otplib` or minimal native Node crypto implementation) for RFC 6238 compliance and QR code generation (`qrcode`).

## Done When

- [ ] `make seed RUN=512` initializes PostgreSQL 16 schema (`actors`, `spaces`, `memberships`, `items`, `artifacts`, and authentication/credential tables) and creates initial test fixtures (seeded password user, OAuth-linked user, 2FA-enabled user, and initial file artifacts) idempotently without duplicate records.
- [ ] Multipart file upload handles both item artifacts (`kind: "file"`) and user avatars, streaming files directly to the designated Docker volume (`/data/uploads`) while enforcing file size limits and validating MIME types via magic bytes.
- [ ] Space-scoped streaming endpoint (`GET /api/spaces/:space_id/artifacts/:id/download`) verifies space membership permissions: authorized space members can stream/download files with correct `Content-Type` and safe `Content-Disposition`, while outside users and unauthenticated requests receive `403 Forbidden` / `401 Unauthorized`.
- [ ] Deleting an artifact removes its database record and unlinks the corresponding physical file from the Docker volume, preventing orphaned disk storage.
- [ ] OAuth 2.0 authentication flow (featuring a built-in mock 42 OAuth provider for offline testing alongside live provider configuration) successfully logs in a user and automatically links to an existing account if the email matches, without corrupting or wiping password credentials.
- [ ] 2FA workflow supports TOTP enrollment with QR code display, validates 6-digit one-time codes with time drift tolerance, stores secrets symmetrically encrypted at rest, and provides a set of single-use recovery codes that are invalidated upon use.
- [ ] The web UI at `http://localhost:3512` provides an interactive diagnostic control plane to switch personas, test authorized vs. unauthorized file downloads, upload avatars and artifacts with live preview, and execute OAuth and 2FA login flows.
- [ ] Repeatedly running `make seed RUN=512` on an existing database is completely idempotent and preserves existing volume files.
- [ ] Scoped documentation (`docs/run-512/design.md`, `docs/run-512/frontend.md`, `docs/run-512/backend.md`, `docs/run-512/NOTES.md`) is maintained.
