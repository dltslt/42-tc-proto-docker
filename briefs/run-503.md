# run-503: Hybrid SQL/NoSQL Intersection & Space Policy Enforcement

**Kind:** exploration  
**Port:** 3503  
**DB:** hybrid (PostgreSQL 16 Alpine + MongoDB 7)  
**Question:** When actors, spaces, and organization memberships are stored in PostgreSQL and items and blockers live in MongoDB, which intersection pattern (SQL pre-flight lookup, cached capability claims, or denormalized document replication) best enforces space policies and cross-space dependency privacy without incurring prohibitive latency or synchronization leaks?

## Scenario

A developer with a systems and C/C++ background is evaluating Lerch's hybrid database architecture. In this architecture, PostgreSQL serves as the relational source of truth for accounts, organization spaces (`personal` vs `organization`, `U5`), and space memberships (`admin`, `member`, and guest policies), while MongoDB stores high-volume work items and directed blocker graphs. Because relational foreign keys cannot cross database engines into MongoDB, the Nitro server layer must enforce authorization, validate boundaries, and prevent cross-space data leaks.

The user explores the system through an interactive diagnostic workspace:
1. **Persona Switching & Space Hierarchy:** The developer switches personas in the header between `Admin Alice` (admin across spaces), `Member Bob` (member of General and Engineering spaces), and `Guest Charlie` (subject to guest non-team policy: sees only public items, with restricted visibility into higher levels). The interface immediately updates the visible workspace, showing personal and organization spaces and their contained items.
2. **Three Enforcement Patterns:** The developer can switch the active backend policy enforcement mechanism via a diagnostic control to observe how `can(actor, action, resource)` is resolved:
   - **Pattern 1 (SQL Pre-Flight Lookup):** Every item request triggers a synchronous SQL query against PostgreSQL to retrieve the actor's verified `space_id` memberships and roles, injecting `{ space_id: { $in: allowedIds } }` directly into the MongoDB document query.
   - **Pattern 2 (Cached Capability Claims):** Space memberships and roles are cached in session/token state with an adjustable Time-To-Live (TTL). MongoDB queries read the allowed space IDs directly from memory without a PostgreSQL network hop.
   - **Pattern 3 (Denormalized Replicated Memberships):** Space access lists are replicated into MongoDB collections or embedded on items (`authorized_actor_ids`), allowing MongoDB to filter documents natively using single-collection indexes.
3. **Revocation & Staleness Simulator:** The developer can execute a live membership revocation (e.g., removing Bob from the Engineering space) and trigger subsequent reads and mutations. The diagnostic UI highlights the failure modes: immediate rejection (Pattern 1), unauthorized read window during cache validity (Pattern 2), or dual-write synchronization latency (Pattern 3).
4. **Cross-Space Blocker Resolution & Information Leakage (`§2.8 Q2`, `§2.8 Q1`):** Item A in the General space is blocked by Item B in a confidential Executive space. When viewed by Member Bob (who has no access to Executive), the prototype allows toggling between three dependency resolution strategies:
   - *Full Leak:* Displays Item B's title and metadata, violating the space boundary.
   - *Opaque Blocker Stub:* Masks Item B's title (rendered as `"Restricted Dependency"` in an opaque card) while preserving its `severity` (`cannot do anything`) and `state` so Bob can triage progress without exposing confidential details.
   - *Strict Silo:* Rejects or conceals cross-space blockers entirely.
5. **Telemetry & Query Inspector:** A persistent diagnostic drawer shows the exact SQL and MongoDB queries executed for each action, round-trip latency (ms), and an automated security audit badge indicating whether any unauthorized document or field leaked across space perimeters.

To keep the exploration focused strictly on the hybrid intersection and policy enforcement, full user authentication flows (OAuth, 2FA, password hashing), real-time WebSockets, and full-text search indexing are intentionally omitted.

## What to Evaluate

### 1. Visual & Presentation Aspects
- **Space & Role Context:** Clear visual cues distinguishing between personal spaces, team organization spaces, and restricted spaces, alongside badges for active roles (`admin`, `member`, `guest`).
- **Cross-Space Blocker Presentation:** Visual contrast between standard internal dependencies and redacted "Restricted External Blocker" stubs (displaying blocker severity badges such as `cannot do anything` or `will be stuck` while obscuring private space titles and descriptions).
- **Diagnostic Telemetry Overlay:** Readability of the live query inspector, contrasting the execution time of relational SQL membership queries versus MongoDB document fetches, with clear hit/miss indicators for cached claims.
- **Permission Failure Feedback:** Clean, informative UI feedback for unauthorized operations (e.g., non-disruptive 403 indicators or inline disabled states) rather than abrupt layout breaks.

### 2. Procedural & Workflow Aspects
- **Persona Context Switching:** Keystroke efficiency and immediacy when alternating between administrative, member, and guest personas to audit data visibility.
- **Membership Management & Revocation:** Simplicity of adding, modifying, or revoking space memberships in PostgreSQL and immediately observing downstream effects on item access.
- **Cross-Space Blocker Triage:** The workflow friction of managing dependencies that cross organizational boundaries when team members have asymmetric space permissions.
- **Failure Mode Recovery:** How the interface and API handle revoked actors attempting in-flight edits or stale reads.

### 3. Technology & Stack Choices
- **Relational Data Access (`W5`):** Ergonomics, type safety, and overhead of using an ORM or query builder in Nitro to manage relational membership tables (`spaces`, `actors`, `memberships`) compared to raw queries.
- **Cross-Database Referential Integrity:** How the application layer manages the boundary between PostgreSQL foreign keys and MongoDB `space_id` references without native cross-engine cascading deletes.
- **Latency & Scalability Trade-offs:** The measured round-trip latency penalty of synchronous pre-flight SQL checks (Pattern 1) versus memory/token-cached claims (Pattern 2) versus replicated document arrays (Pattern 3).
- **Synchronization Complexity:** The implementation complexity and operational risks of keeping denormalized member arrays in MongoDB synchronized with PostgreSQL source-of-truth records during membership mutations.
