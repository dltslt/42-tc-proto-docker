# run-505: Per-Space WebSocket Transport, Presence & Reconnect Resync

**Kind:** interaction-lab  
**Port:** 3505  
**DB:** postgres  
**Question:** Which Nuxt/Nitro WebSocket architecture reliably handles per-space channels and friend presence inside Docker, and how do event-delta replay vs. snapshot refetch and fractional indexing vs. integer reordering compare for reconnect resilience and concurrent kanban collaboration?  

## Scenario

A developer with a systems and C/C++ background wants to evaluate real-time collaboration mechanics (`W2`, `U1`, `§2.9 Q1`) without relying on opaque cloud services. They launch the prototype at `http://localhost:3505`, which provides a multi-session diagnostic environment simulating two collaborating team members (e.g., Alice and Bob) working inside a shared organization space.

Alice and Bob are mutual friends and members of the same space. When both clients connect, their real-time presence indicators reflect "Online" status driven by periodic WebSocket heartbeat pings. Alice creates an item and moves existing items across kanban columns (`unstarted`, `started`, `done`). Bob's board updates immediately via per-space pub/sub broadcast without manual page reloads or HTTP polling.

To test real-world network instability, the developer triggers a simulated network drop on Bob's client (e.g., a 15-second socket blackout). While Bob is disconnected, Alice makes several updates: moving cards, updating item titles, and changing a blocker state. When Bob's client reconnects, the system automatically detects the disconnect gap and triggers state resynchronization. The developer can toggle between two resynchronization modes to compare their behavior:
1. **Event Cursor Delta Fetch:** Bob's client submits its `last_seen_event_id`, and the server returns only the append-only `events` logged since that cursor. Bob's client replays the deltas sequentially, updating local reactive state with minimal network payload while preserving active UI scroll position and focus.
2. **Full State Snapshot Refetch:** Bob's client discards local state and requests the full space entity hierarchy via REST/Nitro API, rebuilding the entire board from scratch.

Next, the developer tests concurrent mutations: Alice and Bob simultaneously drag two different items into adjacent positions within the same kanban column. The developer toggles between two ordering strategies to compare server behavior and conflict frequency:
1. **Fractional Indexing (`lexorank` / float midpoint):** Each move calculates a midpoint float between neighbor items and updates solely the dragged item's position, eliminating cascading SQL updates and lock contention.
2. **Integer Shift Reordering:** Each move executes a transactional SQL shift (`UPDATE items SET position = position + 1 WHERE ...`), demonstrating lock serialization, database query overhead, and race conditions during overlapping moves.

A persistent diagnostic HUD displays real-time WebSocket frame traffic, round-trip heartbeat latency, reconnection timing, sync payload sizes, and connection status badges (`Connected`, `Severed`, `Reconnecting`, `Synchronized`).

To maintain prototype focus, collaborative rich-text CRDT editing (`W7`) is deferred to `run-506`, persistent 1-to-1 chat messaging (`W3`) is deferred to `run-511`, and full user authentication / RBAC policies (`U5`) are deferred to `run-503`.

## What to Evaluate

### 1. Visual & Presentation Aspects
- **Multi-Client Synchrony:** Smoothness of live card transitions, additions, and column movements across separate browser sessions without visual artifacts or unwanted layout shifts.
- **Presence Indicators:** Clear visual feedback for friend online/offline states, transitioning promptly on connection open, heartbeat timeout, or client disconnect.
- **Diagnostic Inspector HUD:** Live stream of inbound and outbound WebSocket frames, displaying frame type, channel topic (`space:<id>` or `user:<id>`), payload size, timestamp, and latency.
- **Resynchronization Feedback:** Observable UI states during reconnect (`Severed` $\to$ `Reconnecting` $\to$ `Catching Up...` $\to$ `Synchronized`), displaying metrics for missed events recovered vs. snapshot replacement.

### 2. Procedural & Workflow Aspects
- **Network Drop & Catchup Workflow:** Evaluating the developer experience of simulating a 5s to 30s network disconnect, verifying that zero events are lost, and validating that the client board achieves strict consistency with the server.
- **Event-Delta vs. Snapshot Recovery:** Comparing the procedural friction of event delta replay (compact payloads, continuous UI continuity) against full snapshot refetch (simpler client-side code, potential UI flicker and scroll reset).
- **Concurrent Kanban Move Resolution:** Experiencing how simultaneous column reorders are handled in practice—evaluating whether cards interleave smoothly without collisions or trigger conflicting position states.
- **Heartbeat & Disconnect Timing:** Testing ping/pong intervals (e.g., 5s heartbeat, 15s timeout threshold) to balance immediate offline detection against false positives from minor network hiccups.

### 3. Technology & Stack Choices
- **Nitro WebSocket Architecture (`crossws`):** Assessing the ergonomics, reliability, and developer experience of Nitro's native WebSocket hooks (`open`, `message`, `close`, `error`) running inside a Docker container behind port `3505`.
- **Database & Query Impact of Ordering Strategies:** Measuring PostgreSQL query execution and lock overhead: single-row fractional position update (`UPDATE items SET position = $1 WHERE id = $2`) versus cascading sibling shifts under integer ordering.
- **Event-Cursor Delta Query Performance:** Efficiency of retrieving delta records from the PostgreSQL `events` log (`WHERE space_id = $1 AND id > $2 ORDER BY id ASC`) compared to full board tree queries.
- **Connection State & Socket Management:** Node.js process memory footprint and connection tracking under multiple concurrent WebSocket connections and room subscriptions.
