# Brief: run-101 — A foundation to build the whole product on

## Scenario

Lerch needs a base that later features can be added to without big rewrites. Data and APIs
are the product, and every interface is a replaceable client of them. The question this run answers:

> Can a backend-first foundation carry a rich, playground-style board, with each feature
> added as a separate module and no schema or API rewrite?

The focus is the backend. If it is done properly, the interface on top stays easy to add and change.

## Stack

- `DB=postgres`, started from `prototypes/template/`. No code is copied from other runs.
- Nuxt 4 and Nitro, PostgreSQL 16, Drizzle ORM (pinned version) with versioned migrations.
- `zod` for all input validation, with schemas shared between server and browser.
- Nuxt UI and Tailwind CSS.
- Vitest for API tests, Playwright with Chromium for browser tests.

## Architecture

### Modules

Each feature is a Nuxt layer: a folder with its own schema, routes, stores and components.
Dependencies point one way, and views never import each other.

```text
core ← workspace ← items ← sync ← views (board, tree, details)
```

| Layer | Owns |
|---|---|
| `core` | Database client, transaction wrapper, errors, `getActor()`, `can()`, event writer, view registry |
| `workspace` | Spaces, actors, memberships, columns, persona and space switchers |
| `items` | Item schema and rules, API routes, store, action path |
| `sync` | Live update stream and its browser client |
| `board`, `tree` | View plug-ins |
| `details` | Side panel |

### Server write path

Every write takes the same path. Routes stay thin and hold no business rules.

```text
route → zod validation → getActor() → can(actor, action, resource) → service
                                                                       └ one transaction: data + event
```

All rules live on the server, so no client can put the data in a bad state.

### Data model

| Table | Columns |
|---|---|
| `spaces` | `id`, `name`, `type` (`personal`, `organization`) |
| `actors` | `id`, `name`, `kind` (`human`, `agent`) |
| `memberships` | `space_id`, `actor_id` |
| `columns` | `id`, `space_id`, `name`, `state`, `position` |
| `items` | `id`, `space_id`, `parent_id`, `type`, `title`, `description`, `state`, `column_id`, `position`, `lead_id`, `version`, `created_at`, `updated_at` |
| `events` | `id`, `space_id` (optional), `target_kind`, `target_id`, `actor_id`, `type`, `changes`, `created_at` |

- **Columns** are the space's shared workflow, not a board setting. Each maps to a state.
- **Column and state move together:** the server keeps them consistent. `discarded` items stay in the data, and the board hides them.
- **Order** is kept among siblings using fractional text keys, so a move rewrites only the moved item. Ties are broken by `id`.
- **Events** are append-only and generic: they can target anything, not only items. Each stores the old and new value of every changed field.

### Simultaneous changes

- Every write runs in a transaction, so an item and its event are saved together or not at all.
- `version` goes up only when `title` or `description` changes. Saving either one requires the version the user started from. A mismatch returns 409 with the current item.
- Moves, state changes and other fields do not check the version, and the latest write wins. A move therefore never conflicts with a text edit.
- Clients send only the fields that changed.
- A parent change takes a per-space lock inside its transaction, so two simultaneous moves cannot create a cycle.

### API

Everything lives under `/api/v1`, and our own interface gets no private routes.

| Route | Purpose |
|---|---|
| `GET /actors` | Personas for the switcher |
| `GET /spaces` | Spaces of the current actor |
| `GET /spaces/:id/columns` | Columns of a space |
| `GET /spaces/:id/stream` | Live updates (Server-Sent Events) |
| `GET /items?space_id=&limit=&cursor=` | List, returned as `{ data, next_cursor }` |
| `GET /items/:id` | One item |
| `POST /items` | Create: a title alone is enough |
| `PATCH /items/:id` | Edit fields, with `expected_version` for text |
| `POST /items/:id/move` | Change parent, column or order |
| `DELETE /items/:id?mode=subtree\|lift` | Delete with its children, or move the children up |

- Errors share one shape and use readable messages: 400 invalid input, 401 no actor, 403 not allowed or wrong space, 404 not found, 409 conflict.
- Deleting an item that has children without a `mode` returns 409.

### Live updates

- Each committed change sends a small Postgres `NOTIFY` naming the changed target, and every server process forwards it to the browsers in that space.
- The browser then fetches the current item, so the order messages arrive in does not matter.
- Items with a save in progress are skipped until that save finishes.
- A reconnect refetches the whole space.

### Browser action path

Each edit is one small action with four parts: apply, send, roll back and undo. It lives in a
library separate from the Vue screens, so any view can use it.

### Text conflicts

Ada and Ben edit the same description, and Ada saves first:

1. Live sync tells Ben that Ada changed it. His text is not replaced while he types.
2. His save returns 409, and his text stays in the editor.
3. He sees both versions and chooses keep mine, use Ada's, or merge by hand.

Drafts are also kept in `localStorage`, so a crash or closed tab does not lose them. The event
log keeps the replaced text.

### Prepared for later, not built now

- `getActor()` is the only place that knows who is calling. The persona lives in a cookie, so real auth or API keys replace one function.
- `can()` is called on every write and allows everything for now.
- The browser uses relative URLs, so adding HTTPS needs no code changes.
- Views register through the view registry, so new views need no changes to existing ones.

The persona switcher is not secure, so this run must not be deployed publicly.

## Tasks

Each task leaves the app working and is reviewed before the next one starts.

1. **Skeleton:** scaffold, authorship file, layers, page shell and view registry.
2. **Database:** Drizzle, migrations, all tables above and an idempotent seed. `make seed` applies migrations first.
3. **Identity:** `getActor()`, `can()`, space isolation, and persona and space switchers.
4. **Read path:** list and detail routes with pagination, and a simple board as the first view plug-in.
5. **Write path:** create, edit, move and delete, with transactions, events, version checks and cycle protection. Tests cover simultaneous edits.
6. **Action path:** instant updates, rollback, undo and keeping the draft on a conflict. Undo covers moves and field edits, while delete asks for confirmation instead.
7. **Live sync:** stream route and browser client, with changes appearing across two browsers.
8. **Side panel:** full editing, the conflict screen and the delete choice.
9. **Tree view:** a second view plug-in, to prove views are swappable.
10. **Drag:** pointer-based drag to change column and order, with touch support and a non-drag "Move to" menu.
11. **Hierarchy:** expandable boxes on the board and drag to nest.

Tasks 1 to 7 build the backend and the paths everything else uses. Tasks 8 to 11 should need
no schema change and no API change. If one does, it is recorded in `NOTES.md`, because it
means the foundation missed something.

## Out of scope

Everything else, including multi-select, saved views, custom fields and tags.

## Done when

1. `make seed RUN=101` applies migrations and seeds, and can run repeatedly without errors or duplicates.
2. Switching persona or space changes what is shown, and items of one space are never visible in another.
3. A title alone creates an item, and it appears immediately in both views.
4. Every write creates its event in the same transaction, and a failed write leaves neither behind.
5. Invalid input returns a 4xx with a readable message, never a 500.
6. Tests show that simultaneous text edits return 409, a move never conflicts with a text edit, and simultaneous moves cannot create a cycle.
7. A rejected save rolls back on screen, and undo reverts the last move or field edit.
8. A change in one browser appears in a second browser without a reload, and a reconnect recovers cleanly.
9. In the two-user description conflict above, Ben's text is never lost.
10. Dragging a card changes its column and order and persists after a reload. Touch and the "Move to" menu do the same.
11. Expanding a card shows its children on their own nested board, and dragging one card onto another nests it.
12. Board and tree can each be removed without changing the other.
13. Browser flows pass in Chromium with no console warnings or errors.
