# Brief: run-102 — A stable, modular contract any client can use

## Scenario

Lerch needs a data model and an API that outlive any interface. The API is the product. A
browser UI, an agent and a plain script are all equal clients of it. The question this run answers:

> Can one versioned `/api/v1` contract, defined once in Zod schemas and built from small
> modules, carry the Lerch baseline (spaces, actors, items, hierarchy, columns, events) so
> that later features are added as new modules, with no rename and no change to existing ones?

The focus is the database and the API. There is no product UI. The only page is a generated API reference.

## Stack

- `DB=postgres`, started from `prototypes/template/`. No code is copied from other runs.
- Nuxt 4 and Nitro routes, PostgreSQL 16, Drizzle ORM (pinned version) with versioned migrations.
- `zod` schemas define every request and response: types, validation and the OpenAPI document.
- Vitest for API tests, using plain HTTP calls against a separate test database.

## Principles

- **The contract is stable:** add fields or endpoints, never rename or remove within `v1`.
- **Routes are thin:** they validate, identify the caller, check permission and call a service. No business rules live in a route.
- **All rules live on the server and in the database**, so no client can put the data in a bad state.
- **Everything is testable with plain HTTP.**
- **Shared vocabulary:** names and baseline fields follow `specs/data-foundation.md`. Anything added is recorded in `NOTES.md`.

## Modules

Each feature is a Nuxt layer: a folder with its own Drizzle schema, Zod schemas, routes,
services and tests. Nuxt merges the layers into one app, and each layer's `server/api/` routes
are still registered by file path.

```text
core ← workspace ← items ← events
                     ▲
                     └── tags (added last, as the proof)
```

| Layer | Owns |
|---|---|
| `core` | Database client, transaction wrapper, error shape, pagination helper, OpenAPI builder, `can()` and its action registry, event writer and event type registry |
| `workspace` | Spaces, actors, memberships, columns, `getActor()` |
| `items` | Item schema and rules, item routes |
| `events` | The event table and its read route |
| `tags` | Added in the last task: tags and item links |

Rules for layers:

- Dependencies point one way, as in the diagram. A layer never imports from a layer above it.
- A module never reads or writes another module's tables directly. It calls that module's service.
- A module registers its own event types and its own `can()` action names (for example `item.create`). Nothing central is edited when a feature is added.
- Each layer's schema lives in the layer. One `drizzle.config.ts` collects them into one ordered migration history.
- A layer can be removed without breaking the others, unless another layer depends on it.
- `GET /api/v1/` lists the loaded modules and the contract version, so clients and tests can see which layers are present.

## Server write path

```text
route → zod validation → getActor() → can(actor, action, resource) → service
                                                                       └ one transaction: data + event
```

- `getActor()` is the only place that knows who is calling. For now it reads an `X-Actor-Id` header. Real auth or API keys replace this one function.
- `can()` is called on every write and allows everything for now. Actions come from the registry.
- The header is not security. This run must not be deployed publicly.

## Data model

**Conventions:** uuid ids (treated as opaque by clients), snake_case names, `timestamptz` for times, real foreign keys. Every table has `id`, `created_at`, `updated_at`, except `events` (see below).

| Table | Columns |
|---|---|
| `spaces` | `name`, `type` (`personal`, `organization`) |
| `actors` | `name`, `kind` (`human`, `agent`) |
| `memberships` | `space_id`, `actor_id` (primary key on both) |
| `columns` | `space_id`, `name`, `state`, `position` |
| `items` | `space_id`, `parent_id`, `type`, `title`, `description`, `state`, `column_id`, `position`, `lead_id`, `version` |
| `events` | `id` (bigint identity), `space_id` (optional), `target_kind`, `target_id`, `actor_id`, `type`, `changes`, `created_at` |

- **Personal tasks** live in a personal space, one per human actor. There is no nullable `space_id`.
- **Items** carry `type` (`project|epic|story|task`) and `state` (`unstarted|started|done|discarded`). A title alone is enough to create one. `description` is markdown and defaults to `''`. Children are the rows where `parent_id` matches.
- **Columns** are the space's shared workflow, not a board setting. Each maps to a `state`. Column and state move together, and the server keeps them consistent. `discarded` items stay in the data.
- **Order** among siblings is a fractional text key in `position`, so a move rewrites only the moved item. Ties are broken by `id`, and the move logic handles two siblings with the same key.
- **Events** are append-only and generic. They can target anything, so `target_id` has no foreign key. `changes` maps each changed field to `{ from, to }`. `type` is an open string such as `item.created`, registered by the module that writes it.
- **Event ids** are a `bigint` identity, so they have a stable order. `?after=<id>` is a reliable replay point, and later real-time, notifications and export can build on the log.
- **Human details** (`email`, avatar, credentials) are not in the baseline. They are an extension table later, so agents are not forced to have them.

### Rules enforced by the database

- An item's column and parent are in the same space as the item (composite foreign keys).
- A column cannot be deleted while an item uses it (`ON DELETE RESTRICT`).
- An item's `state` matches its column's `state`.
- Events keep foreign keys to actors and spaces. As a result, **v1 has no delete route for spaces or actors.** Archiving them, or changing the rule, comes later and is recorded in `NOTES.md`.

### Simultaneous changes

- Every write runs in a transaction, so an item and its event are saved together or not at all.
- `version` goes up on every update of `title`, `description`, `type` or `lead_id`. Updates say which version they expect, and a mismatch returns 409 with the current item.
- Moves and state changes do not check the version, and the latest write wins. A move never conflicts with a text edit.
- A parent change takes a per-space lock inside its transaction, so two simultaneous moves cannot create a cycle.

## API

Base path `/api/v1`, plural nouns, snake_case JSON, ISO 8601 UTC times.

| Route | Purpose |
|---|---|
| `GET /` | Loaded modules and contract version |
| `GET /actors` | List actors |
| `GET /spaces` | Spaces of the current actor |
| `GET /spaces/:id/columns` | Columns of a space |
| `GET /spaces/:id/events` | Event log, filtered by `type`, `target_kind`, `target_id`, `after` |
| `GET /items?space_id=` | List with filters and cursor pagination |
| `GET /items/:id` | One item |
| `POST /items` | Create: a title alone is enough |
| `PATCH /items/:id` | Edit fields, with `expected_version` for versioned fields |
| `POST /items/:id/move` | Change parent, column and position in one call |
| `DELETE /items/:id?mode=subtree\|lift` | Delete with its children, or move the children up |
| `GET /openapi.json` | The contract, generated from the Zod schemas |

- **Lists** return `{ data, next_cursor }` with `?limit=50&cursor=…`, `?sort=position` or `?sort=-created_at`, and filters (`state`, `column_id`, `parent_id`, `lead_id`, `q`).
- **Errors** share one shape, `{ "error": { "code", "message", "fields" } }`, with status 400 invalid input, 401 no actor, 403 not allowed or wrong space, 404 not found, 405 wrong method (with an `Allow` header), 409 conflict.
- Deleting an item that has children without a `mode` returns 409.
- `?include=` is not built. Responses hold ids only.
- Every write also appends an event, in the same transaction.

## Tasks

Each task leaves the app working and is reviewed before the next one starts.

1. **Skeleton:** scaffold, authorship file, layers, module loader, `GET /api/v1/`, error helpers, the OpenAPI route and a health check with a test.
2. **Database:** Drizzle collecting each layer's schema into one migration history, all tables above and an idempotent seed. `make seed` applies migrations first.
3. **Identity and read path:** `getActor()`, `can()` with its action registry, space isolation, then the actors, spaces, columns and item read routes with pagination, filters and sorting.
4. **Write path:** create, edit, move and delete with transactions, events, version checks, tied order keys and cycle protection.
5. **Event log:** the events route with filters and `after`, and a test that every write produced exactly one event.
6. **Extension proof:** add `tags` as a new layer (table, routes, event types, `can()` actions) without editing any existing layer. Any edit to an existing file is recorded in `NOTES.md`, because it means the foundation missed something.
7. **Hardening:** a contract test for every route (success and each error), a concurrency test with two real connections, a removal test for each removable layer, then freeze `v1`.

## Out of scope

Everything else, including any UI, real-time transport, import and export, artifacts,
comments, blockers, scheduling, file uploads, login and roles.

## Prepared for later, not built now

- Artifacts, comments, blockers and allocations are new layers, added by migration. None changes an existing name.
- Human extension table for `email`, avatar and credentials. `memberships.role` and `api_keys` are also later additions.
- Real-time updates can read the `events` table, since events are appended in the same transaction as the write.
- Import and export can use the same Zod schemas as the API.
- `can()` can be replaced with real rules without touching any route.
- `Idempotency-Key` on `POST`, so agents and scripts can retry without creating duplicates.
- Archiving spaces and actors, or anonymising their events, once a privacy rule exists.

## Done when

1. `make seed RUN=102` applies migrations and seeds, and can run repeatedly without errors or duplicates.
2. `GET /api/v1/openapi.json` describes every route, and its schemas are generated from the same Zod schemas that validate requests.
3. A request without `X-Actor-Id` returns 401. An actor never sees or changes items of a space they are not a member of (403).
4. A title alone creates an item in the first `unstarted` column of the space.
5. Every write creates its event in the same transaction, and a failed write leaves neither behind.
6. Invalid input returns a 4xx with the shared error shape, never a 500.
7. Tests show that simultaneous text edits return 409, a move never conflicts with a text edit, and simultaneous moves cannot create a cycle.
8. A move between two siblings that share the same order key returns a valid result, not a 500.
9. Deleting an item with children needs a `mode`, and both modes leave the hierarchy consistent.
10. The list route paginates through the whole seeded set without gaps or repeats, and returns each filter and sort correctly.
11. `?after=<event id>` returns exactly the events written after that id, in order.
12. Every route is exercised with plain HTTP calls, including from a script outside Nuxt, using only the OpenAPI document.
13. `tags` is added with no edits to existing layers, and removing `tags` leaves every other route working.
14. `GET /api/v1/` lists exactly the layers that are loaded.
