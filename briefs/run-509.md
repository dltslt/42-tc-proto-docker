# run-509: Cross-Space Analytics Aggregation & Server-Side Export Engine

**Kind:** benchmark  
**Port:** 3509  
**DB:** postgres  
**Question:** How should the personal welcome dashboard (`DA1`) aggregate items, blockers, and weekly completed event metrics across multiple spaces at scale (up to 50,000 records)—comparing live SQL `GROUP BY` aggregations against PostgreSQL materialized views—and what is the most reliable, lightweight architecture for generating PDF dashboard snapshots and streaming CSV exports in a Node/Nitro container?

## Scenario

A team of developers with a C/C++ systems background is building the personal welcome page and analytics dashboard (`DA1`) for Lerch. When a user logs in, the welcome dashboard provides an instant cross-space operational overview of the work they care about across all personal and organization spaces where they hold membership (`§2.6`, `specs/product-v9.md`).

The dashboard requires 4 core interactive charts driven by cross-space queries:
1. **Weekly Completed Items (Line Chart):** Items finished per week over a rolling time window (e.g., last 8 weeks), aggregated from immutable completion records in the append-only `events` log (`§2.5`).
2. **Open Items by Kanban Column (Bar Chart):** Count of non-completed items (`state != 'done'`) grouped by board column (`backlog`, `in progress`, custom columns).
3. **Item Distribution by Space (Pie / Donut Chart):** Total active items distributed across each space the user belongs to.
4. **Blocker Severity Distribution (Bar Chart):** Open items grouped by the 4-step blocker severity scale (`cannot do anything`, `will be stuck`, `slowed down`, `nice to have`) to surface urgent impediments (`§2.3`).

The developer launches the prototype at `http://localhost:3509` to evaluate three critical backend architectural challenges:

1. **Cross-Space Authorization & Aggregation Strategies at Scale:**
   Because Lerch enforces space-scoped security policies (`§1.2`, `§2.8`), the dashboard must strictly restrict aggregations to spaces where the active user is a member (`WHERE space_id IN (SELECT space_id FROM memberships WHERE actor_id = :current_user)`). The developer tests how query latency and memory scale when aggregating across 500 curated baseline records versus a synthetic benchmark dataset of 50,000 items and events, directly comparing three aggregation architectures:
   - *Strategy A (Live Parameterized SQL Aggregation):* Direct parameterized SQL queries using composite indexes on `(space_id, state)`, `(space_id, kanban)`, and `events(space_id, type, created_at)`, paired with `generate_series` to preserve zero-count weeks.
   - *Strategy B (PostgreSQL Materialized Views):* Pre-aggregated relational views (`REFRESH MATERIALIZED VIEW CONCURRENTLY`) evaluated against on-demand queries for refresh latency, query response time, write amplification, and data freshness trade-offs.
   - *Strategy C (Incremental In-Memory / Redis-style Cache):* Nitro server-cached aggregate payloads keyed by user and date filter, invalidated or updated on relevant mutation events.

2. **Real-Time Dashboard Synchronization (`W2` vs. Polling):**
   When an item is completed, created, moved between kanban columns, or flagged with a blocker in a background tab or by another team member, the dashboard must reflect the change (`§2.6`). The developer tests two synchronization models over WebSockets:
   - *Pattern A (Debounced Invalidation Signal):* The server broadcasts a lightweight invalidation message (`{ type: "dashboard_invalidated", space_id }`); the client debounces incoming signals (e.g., 500ms) and triggers a fast re-fetch of the aggregated metrics.
   - *Pattern B (Fine-Grained Metric Delta Pushing):* The server computes exact numerical deltas (`{ chart: "kanban", delta: { in_progress: -1, done: +1 } }`) and pushes them live over the socket for instant client-side state adjustment without database roundtrips, measuring code complexity and client-server drift risks.

3. **Export Engine Architecture (PDF Snapshots & Streaming CSV):**
   The developer evaluates how best to satisfy the `DA1` requirement for PDF snapshots and CSV data export without introducing heavy container bloat or blocking the Node single-threaded event loop:
   - *Streaming CSV Export:* Generating and streaming RFC 4180 compliant CSV files with streaming HTTP response headers (`Content-Disposition: attachment`), measuring time-to-first-byte and memory usage at 50k rows.
   - *Lightweight Server-Side Vector PDF (`pdfkit` / `unpdf`):* Rendering high-resolution PDF reports directly in Nitro using a headless vector library, drawing layout tables, executive KPI cards, and vector charts without browser dependencies.
   - *Client-Side Canvas/SVG Capture (`jspdf` / `html2canvas`):* Capturing client DOM/SVG chart elements into a downloadable PDF entirely in the browser.
   - *Resource & Container DX Comparison:* Comparing the memory footprint, execution latency, and binary size overhead of server-side headless libraries against full headless browser solutions (e.g., Puppeteer/Chromium, which adds >300MB container overhead and 150MB+ RAM per render).

Full interactive kanban drag-and-drop boards, complex rich-text editing, OAuth registration flows, and 1-to-1 private chat are intentionally omitted to focus strictly on query aggregation performance, multi-space privilege filtering, real-time sync mechanics, and export pipeline efficiency.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **DA1 Welcome Dashboard Layout:** A clean diagnostic analytics view displaying the 4 required charts (weekly finished line chart, open kanban bar chart, space distribution pie chart, blocker severity bar chart) alongside executive KPI summary cards (Total Active Items, Blocked Items, Velocity/Week).
- **Interactive Filter & Persona Controls:** Responsive controls to toggle date filters (`7d`, `30d`, custom date range), filter by specific spaces or view all member spaces, and switch active personas (e.g., User with 4 active spaces vs User with 1 space) to verify strict data isolation.
- **SQL Execution & Query Plan Inspector:** Side-by-side diagnostic cards showing the raw SQL queries, `EXPLAIN (ANALYZE, BUFFERS)` execution plans, index hit rates, buffer reads, and execution timings for each chart widget.
- **Export Fidelity & Layout Inspector:** Side-by-side comparison of the generated PDF document (layout grid, pagination, typography, vector chart clarity) against the live web UI.

### 2. Procedural / Workflow Aspects
- **Cross-Space Permission Enforcement:** Verifying that aggregations strictly exclude items and events from spaces where the current user is not an active member, even under synthetic 50,000-item workloads.
- **Date Filter & Time-Series Continuous Bucketing:** Evaluating how query performance responds to variable date windows and verifying that `generate_series` cleanly fills zero-activity weeks so line charts remain mathematically and visually continuous.
- **Real-Time Mutation & Sync Experience:** Triggering mock item mutations (e.g., marking an item done, reassigning a column, escalating blocker severity) and observing the latency and visual smoothness of debounced re-fetching versus live WebSocket delta pushes.
- **Export Trigger & Download Experience:** Measuring user wait time and UI responsiveness when triggering CSV and PDF downloads under standard (500 items) versus stress-test (50,000 items) conditions.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **Aggregation Engine (`§2.6 Q6`, `DA1`):** Does optimized parameterized SQL with composite B-Tree indexes deliver sub-10ms response times at 50,000 items/events, rendering PostgreSQL `MATERIALIZED VIEW` overhead (maintenance locks, refresh schedules, and data staleness) unnecessary for the primary production stack?
- **Export Engine Architecture (`DA1`):** Evaluating the developer ergonomics, rendering speed, and container resource footprint of a lightweight server-side vector PDF generator (`pdfkit` / `unpdf`) versus client-side SVG/canvas export (`jspdf`), proving that Lerch can deliver professional PDF snapshots without bundling heavy headless Chromium containers.
- **Streaming Response Ergonomics in Nitro:** Assessing how cleanly Nitro handles streaming HTTP responses for large CSV and binary PDF exports without buffering the entire payload in Node process heap memory.
- **Real-Time Sync Protocol (`W2`):** Determining whether debounced invalidation queries provide a significantly simpler, bug-free implementation for C/C++ developers compared to maintaining stateful client-side delta arithmetic across multi-dimensional charts.
