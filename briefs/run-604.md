# run-604: Passive Communication vs. In-App Notification Center

**Kind:** interaction-lab  
**Port:** 3604  
**DB:** none  
**Question:** How should ambient passive workspace cues (in-view card pulses and state indicators) combine with an active unread notification center across all 7 domain entity types without causing alert fatigue, and does contextual auto-clearing or inline `@mention` parsing improve team communication signal-to-noise?

## Scenario

A team of developers with a C/C++ systems background is evaluating the communication and alerting architecture for Lerch. In a team collaboration hub, communication must strike a delicate balance between keeping collaborators informed and avoiding overwhelming alert fatigue. In Lerch, communication is governed by two complementary paradigms:

1. **The Quiet Butler (Passive Communication):** Lerch is built to stay out of the way. When a user is actively viewing a space or kanban board, changes occurring within that space (a card moving across columns, an artifact attached, or a blocker flagged) should surface ambiently—via subtle card pulses, border highlights, or an inline activity ticker—without ringing alarm bells, opening disruptive modal popups, or demanding acknowledgment clicks.
2. **The Notification Center (`Module W6` & `W2`):** When critical actions occur outside the user's active viewport (in other spaces they belong to, or direct personal events like friend requests, private messages, or space memberships), those events must be collected into a central unread notification center accessed via a top-bar bell icon.

The developer launches the prototype on port 3604 with `DB=none` (using an in-memory reactive event store and seeded team fixtures). The interface presents a multi-space workspace alongside an interactive **Simulation & Evaluation Control Bar**.

Through this environment, the developer explores four key interaction challenges:

1. **The 7-Entity Notification Matrix (`§2.9`, `§3.3`, `W6`):**
The developer evaluates how creation, update, and deletion actions across all 7 core notification entities behave:
- `Item`: created, updated, moved across kanban columns, deleted.
- `Artifact`: link attached, file uploaded, removed.
- `Blocker`: severity set (`cannot do anything` $\to$ `nice to have`), updated, cleared.
- `Organization`: created, renamed, deleted.
- `Membership`: user added to or removed from a space/organization.
- `Friend request`: request sent, accepted, or rejected.
- `Private message`: 1-to-1 direct message sent between friends.

2. **Self-Action Suppression & The Active-Space Rule:**
Using the top-bar **Persona Switcher**, the developer toggles between multiple actors (e.g., *Alex* [Team Lead], *Maya* [Frontend Engineer], and *Automated CI Bot*). The developer verifies:
- *Self-action suppression:* When Alex moves a card or resolves a blocker, Alex is never notified of their own action (zero unread badge increments).
- *Active-space boundary:* When Alex is looking at the "Platform Engineering" board, updates made by Maya in that space highlight the card with a gentle ambient glow on Alex's screen, while Alex's top-bar bell counter remains unaffected. However, if Maya modifies an item in the "Design System" space (which Alex is *not* currently viewing), Alex's bell badge increments.

3. **Notification Drawer, Click-to-Navigate & Read-State Strategies (`W6`):**
Clicking the bell icon slides open the Notification Center drawer. The drawer groups events by space and item, displays actor avatars, relative timestamps, and high-contrast entity badges. Clicking any notification card immediately navigates the workspace to that space/item and focuses the relevant entity.
To resolve notification fatigue, the developer toggles between two read-state mechanisms:
- *Manual Acknowledge:* Notifications remain unread until explicitly dismissed or marked read via a checkmark.
- *Contextual Auto-Read:* Navigating into a space or opening an item card automatically marks all associated unread notifications as read, eliminating tedious cleanup clicks.

4. **Direct `@mentions` vs. External Delivery Simulation (`§2.9 Q3`, `§2.9 Q4`):**
- *Direct Mentions:* When an author types `@alex` in an item description or comment, the parser elevates the notification to a prioritized "Direct Mention" tier, badged in high-contrast amber and surfaced in a dedicated "Mentions" tab. The developer tests whether this eliminates the need to notify team members about routine card movements.
- *External Dispatch Simulator:* An inspector drawer demonstrates how Lerch would deliver notifications beyond the in-app UI (simulating Slack webhooks, email digests, and browser push notifications). The developer tests threshold policies—such as routing only direct `@mentions` and critical blockers (`cannot do anything`) to external channels while leaving routine updates strictly in-app.

Full relational/document database persistence, external email servers, live third-party Slack bots, and multi-user WebRTC channels are intentionally omitted to keep the prototype purely focused on frontend interaction ergonomics, reactivity performance, and notification signal-to-noise.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **Ambient Feedback vs. Active Interruption:** Visual contrast between passive cues (subtle CSS border pulse, background fade, inline status change) on active boards versus active cues (red/amber badge counter on the bell icon).
- **Notification Drawer Layout:** Density, visual hierarchy, and readability of the slide-over drawer; clear distinction between entity types (item, artifact, blocker severity, org, membership, friend, DM) using semantic icons and badges.
- **Direct Mention Highlighting:** Visual emphasis for `@username` mentions (distinct color accent, avatar chip, dedicated tab filter) compared to broadcast team updates.
- **Grouped Notifications:** Visual aggregation of rapid successive events (e.g. "Maya moved 3 items and updated 1 blocker in Mobile App") to prevent visual clutter in the feed.
- **External Dispatch Inspector:** Clear visual representation of outbound webhook payloads, mock email digests, and browser push cards.

### 2. Procedural / Workflow Aspects
- **Self-Action Suppression Verification:** Seamless switching between personas (Alex vs. Maya) to immediately confirm that personal actions generate zero notification noise for the actor.
- **Click-to-Navigate Traversal:** Frictionless 1-click hop from a notification card directly into the target space, auto-scrolling to and highlighting the target item or blocker.
- **Read-State Friction:** Experiencing the difference between manual "mark as read" bookkeeping versus contextual auto-clearing upon navigating to an item or space.
- **Simulation Control Ergonomics:** The ease with which a reviewer can inject synthetic events across all 7 entities, flood batch updates, or trigger `@mentions` to test board reactivity and drawer responsiveness.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **Reactive State Architecture:** Using Vue 3 reactivity (`ref`, `computed`, reactive stores) to maintain an append-only event stream in client memory and derive unread counts and grouped feeds with zero rendering lag.
- **Event-to-Notification Mapping:** Ergonomics of transforming raw domain `Event` objects (`target_id`, `actor_id`, `type`, `changes`) into human-readable notification cards with dynamic relative timestamps.
- **Inline Text Parsing:** Client-side regex or tokenization of `@mentions` in comments and descriptions, evaluating whether frontend parsing suffices or if mentions require dedicated backend event schemas.
- **Animation & DOM Stability:** Evaluating lightweight CSS transitions for card glow/pulse effects to ensure passive updates do not trigger layout shifts (CLS) or disrupt ongoing user interactions.
