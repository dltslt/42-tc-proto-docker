# run-507: Public REST API, Hashed Key Auth, Rate Limiter & Actor Identity

**Kind:** slice  
**Port:** 3507  
**DB:** postgres  
**Question:** How should external API requests authenticate and attribute mutations between human key-owners and autonomous agent actors, and how cleanly can Nitro middleware enforce SHA-256 hashed keys, sliding-window rate limiting, and OpenAPI documentation across the 6 core REST endpoints?

## Scenario

A developer or external tool integrator interacts with Lerch via the external REST API (**W4**) rather than the primary web UI.

The prototype provides an interactive diagnostic workbench alongside the public API endpoints:

1. **API Key Generation & Hashed Storage:**
   The developer creates an API key in the diagnostic workbench and configures it for one of two distinct actor identity models:
   - **Model A (Human Key-Owner / Personal Access Token):** The key represents a human user (e.g., "Alice"). Any item creation or mutation made with this key attributes the action to the human user (`actor_id = alice.id`) in the `events` table.
   - **Model B (Autonomous Agent Actor):** The key represents a distinct autonomous agent (`kind: "agent"`, e.g., "Bot: Code Reviewer"). Items created or updated with this key record `actor_id = bot.id` in `events`, and the agent actor can be listed directly in `item.contributors` (§2.10 Q1, foundation for **X1**).
   
   Upon key creation, the plain-text token (prefixed with `lrch_live_`) is displayed exactly once in a modal with a copy button and a security notice explaining that only the SHA-256 hash is persisted in the PostgreSQL `api_keys` table. The developer can also revoke a key, immediately terminating its access.

2. **The 6 Core REST Endpoints & Interactive OpenAPI Docs (`/api/docs`):**
   The developer navigates to `/api/docs`, which renders an interactive OpenAPI / Swagger UI. They can inspect endpoint schemas, supply their Bearer token in the authorization dialog, and execute the 6 required REST operations:
   - `GET /api/items` (list items in a space with state filtering, pagination, and sorting)
   - `POST /api/items` (create a new item in a space)
   - `PUT /api/items/{id}` (update an item's title, description, state, or kanban column)
   - `DELETE /api/items/{id}` (delete an item)
   - `GET /api/artifacts` (list artifacts attached to an item)
   - `POST /api/artifacts` (attach a link or file artifact to an item)

3. **Sliding-Window Rate Limiting (§2.10 Q4):**
   The developer runs burst tests (using an in-browser request generator or a provided bash script) to verify rate-limiting compliance under load:
   - Requests include standard rate-limiting headers: `X-RateLimit-Limit: 60`, `X-RateLimit-Remaining: N`, and `X-RateLimit-Reset: <timestamp>`.
   - Normal traffic within the 60 requests/minute window succeeds with HTTP `200 OK` or `201 Created`.
   - Rapidly firing more than 60 requests within a rolling 60-second window triggers HTTP `429 Too Many Requests` containing a standard JSON error payload and a `Retry-After: <seconds>` header.
   - Supplying an invalid, malformed, or revoked key immediately yields HTTP `401 Unauthorized`.

4. **Audit Trail & Identity Verification:**
   A real-time diagnostic event feed displays mutations recorded in the PostgreSQL `events` table. The developer inspects side-by-side mutations to compare how human-driven changes differ from agent-driven changes in the audit trail and item contributor lists.

Administrative settings, OAuth 2.0 / OIDC provider flows, 2FA credential management, session-based browser logins, complex multi-role fine-grained ABAC, and external webhook delivery queues are intentionally omitted to keep the prototype strictly focused on API key authentication, rate-limit middleware, actor identity attribution, and the 6 REST endpoints.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **Token Revelation UI:** The ergonomics of the "show once" key issuance modal, including clear copy-to-clipboard feedback, token prefix readability (`lrch_live_...`), and explicit security warning that the raw secret is never stored.
- **Interactive API Documentation (`/api/docs`):** Visual clarity and usability of the OpenAPI / Swagger UI interface, inspecting request/response schemas, field validations, and the in-browser "Try it out" authorization workflow.
- **Live Rate-Limit & Traffic Gauge:** Visual diagnostic panel showing remaining request quota (`X-RateLimit-Remaining`), sliding-window time decay, and immediate color-coded HTTP status code counters (`200`, `201`, `401`, `429`).
- **Audit Attribution Inspector:** Visual representation of the `events` table and item detail views, clearly distinguishing human vs. autonomous agent contributions through badges and actor metadata.

### 2. Procedural / Workflow Aspects
- **API Key Lifecycle:** The end-to-end flow of generating, using, scoping (space-scoped vs. global), and revoking keys, verifying that revoked keys are rejected immediately without server restart.
- **Actor Identity Comparison (§2.10 Q1):** Comparing the operational workflow and system clarity when an automated script acts as the human owner (personal access token) versus acting as a registered autonomous agent (`kind: "agent"` appearing in `item.contributors`).
- **Burst Load & 429 Backoff Experience:** Evaluating how external clients experience rate-limit thresholds, validating the precision of the 60 req/min sliding window and adherence to `Retry-After` headers.
- **CLI and Script Integration:** Testing the endpoints using standard developer CLI tools (`curl`, `httpie`) and automated scripts to evaluate JSON response consistency and predictable HTTP error structures.

### 3. Technology / Stack Choices
- **Nitro Server Middleware Ergonomics:** Implementing authentication and rate limiting in `server/middleware/` to intercept requests before reaching route handlers (`server/api/`), measuring request overhead in milliseconds.
- **Sliding-Window Rate Limiting Algorithm:** Evaluating an in-memory sliding-window log (timestamp queue / circular buffer) versus a database-backed or token-bucket approach, analyzing memory usage and behavior under burst load.
- **Cryptographic Hashing & Constant-Time Verification:** Assessing the implementation of SHA-256 key hashing in Node.js `crypto` with `timingSafeEqual` to prevent timing side-channel attacks during key lookup.
- **OpenAPI Generation Tooling in Nuxt/Nitro:** Evaluating DX and developer effort for auto-generating OpenAPI 3.0 documentation (e.g., via Nitro route meta, `@scalar/nuxt`, `nitro-openapi`, or swagger-ui-dist) compared to maintaining hand-crafted JSON/YAML specifications.
