# run-504: Event Log Architecture, Audit Replay & C/U/D Notification Fan-Out

**Kind:** benchmark  
**Port:** 3504  
**DB:** hybrid (PostgreSQL 16 Alpine + MongoDB 7)  
**Question:** Should the notification system (`W6`) derive unread notifications on read from an append-only event log with compact read cursors or fan out dedicated recipient rows on write, and does high-volume event logging and point-in-time audit replay perform better in PostgreSQL or MongoDB?

## Scenario

A team of developers with a C/C++ systems background is architecting the event and notification engine for Lerch. Every significant change in the platform produces an immutable event record, powering item audit history, analytics time-series charts (**DA1**), and the complete Create/Update/Delete (C/U/D) notification matrix (**W6**). The engine must support high volume (100,000 to 500,000 events) without write bottlenecks or slow inbox queries.

The developer launches the prototype on port `3504` (`http://localhost:3504`) and accesses a diagnostic workbench organized into three operational evaluation zones:

1. **Event Stream & Point-in-Time Audit Replay:**  
   The user inspects an append-only event log capturing all 7 target kinds defined in `specs/product-v9.md` (§2.9, §3.3):
   - `item` (create, update, kanban/state move, archive, delete)
   - `artifact` (attach link, upload file, delete)
   - `blocker` (set blocker, update severity, clear)
   - `space` (create, update metadata, archive)
   - `membership` (add user, remove user)
   - `friendship` (request sent, accepted, removed)
   - `message` (send private message)
   
   Selecting any item with a rich mutation history displays an interactive audit timeline. The system reconstructs the item's historical state at any selected event ID by sequentially folding structured `{ from, to }` change deltas from the baseline creation event. The user can also inspect autogenerated progress events (`§2.5 Q4`, such as automated blocker cascading or dependency status updates) to verify whether system-generated events use the exact same schema and replay pipeline as user actions.

2. **Notification Delivery Comparison (Derived on Read vs. Fan-Out on Write):**  
   The developer tests the two primary architectural patterns for delivering in-app notifications (`§3.4 Q1`, `W6`):
   - **Pattern A (Derived on Read):** Every mutation writes a single immutable event ($O(1)$ write). A user's unread notification feed is resolved dynamically on read by querying events for the user's subscribed spaces, filtering out actions triggered by the user themselves (`actor_id != current_user`), and comparing event timestamps/IDs against a compact per-user cursor table (`notification_reads`, e.g. `(actor_id, space_id, last_read_event_id)`).
   - **Pattern B (Fan-Out on Write):** Every mutation writes an event record and immediately inserts $N$ individual recipient rows into a `notifications` table ($O(N)$ writes, where $N$ is the number of active space members). Marking a notification read updates a simple boolean flag (`read = true`) on that recipient's row.
   
   The interface features an interactive persona switcher (switching between the mutating actor, recipient teammates, and non-members) and a space mutation trigger (creating items, moving states, or setting blockers in spaces with 2, 10, and 50 members). The developer can toggle a **30-second sliding debounce window** (`§2.9 Q4`) to observe how rapid consecutive edits (such as dragging an item across multiple columns or quickly editing tags) coalesce into a single notification rather than creating notification floods.

3. **Scale & Storage Engine Benchmark (PostgreSQL vs. MongoDB at 100k–500k Events):**  
   The developer triggers synthetic batch generation of 10k, 100k, and 500k events across both PostgreSQL 16 and MongoDB 7. The harness benchmarks:
   - Ingestion throughput (events per second for single-record inserts and batch commits).
   - Unread inbox query latency (P50, P95, P99) across 10 to 25 joined spaces under high event volume.
   - Point-in-time item state reconstruction speed across deep revision histories.
   - Storage footprint and resource consumption: PostgreSQL table bloat, Write-Ahead Logging (WAL) pressure, and index sizing (B-Tree vs. BRIN on timestamps) versus MongoDB capped collections, time-series collections, and compound index overhead.

Full end-user kanban boards, external push channels (Web Push, email, Slack), and production authentication sessions are intentionally omitted to keep the prototype strictly focused on event logging mechanics, audit reconstruction, and notification fan-out trade-offs.

## What to Evaluate

### 1. Visual / Presentation Aspects
- **Audit Replay & Diff Scrubber:** An interactive timeline and diff view showing step-by-step point-in-time item snapshots side by side with the underlying event delta (`changes` payload).
- **Dual-Pattern Inbox Visualizer:** Side-by-side or toggled view displaying a user's notification inbox generated via Pattern A (derived from event cursors) versus Pattern B (materialized recipient rows), showing unread badge counts and category badges across all 7 target kinds.
- **Self-Action Suppression Clarity:** Immediate visual confirmation that the actor who executed a mutation never receives a notification for their own action, while all eligible space members do.
- **Diagnostic Benchmark Dashboard:** Real-time telemetry panels reporting ingestion rates (events/sec), write amplification ratios ($1\times$ vs $50\times$), unread query response times (ms), and disk usage (MB).
- **Query Plan Transparency:** Expandable panels displaying raw PostgreSQL `EXPLAIN ANALYZE` outputs and MongoDB `executionStats` for both write transactions and unread notification queries.

### 2. Procedural / Workflow Aspects
- **Inbox Triage & Read Cursor Mechanics:** The operational flow of marking individual notifications as read or marking an entire space as read. Evaluating how advancing a compact cursor (Pattern A) compares to bulk-updating individual row statuses (Pattern B) in user experience and database contention.
- **Debounce Window Experience (`§2.9 Q4`):** Simulating rapid-fire updates (e.g. 5 updates in 10 seconds) with the 30-second debounce window toggled ON versus OFF. Evaluating whether coalesced notifications keep teammates informed without creating inbox fatigue.
- **Persona Context Switching:** Switching between different user personas to verify cross-space isolation, recipient delivery accuracy, and authorization boundaries.
- **Point-in-Time State Recovery:** How easily a developer or auditor can pinpoint an item's exact state at an arbitrary historical timestamp or event ID to diagnose regressions or inspect changes.

### 3. Technology / Stack Choices
- **PostgreSQL vs. MongoDB for Append-Only Event Logs:** Comparing PostgreSQL append-only tables (evaluating WAL write load, index maintenance overhead, and BRIN index efficiency on sequential timestamps) against MongoDB collections (standard, capped, or time-series) under 100k–500k events.
- **Pattern A (Derived on Read) vs. Pattern B (Fan-Out on Write):**
  - *Pattern A:* Zero write amplification ($O(1)$ write) and minimal disk storage; but requires indexed join/filter queries across spaces and cursors on read.
  - *Pattern B:* Ultra-fast $O(1)$ read queries (`SELECT ... WHERE user_id = ? AND read = false`); but $O(N)$ write amplification and rapid table growth in large spaces.
- **Replay Ergonomics:** Developer ergonomics in Nitro/TypeScript for rolling forward item deltas in application code versus using database-level recursive queries or aggregation pipelines.
- **Foundation for Analytics (`DA1`):** Evaluating whether the unified event log structure allows efficient aggregate queries (such as counting weekly completed items across spaces) for the upcoming personal welcome dashboard.
