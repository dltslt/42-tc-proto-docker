# run-501: Full Domain Scale & Transaction Boundaries (All 8 Invariants)

**Kind:** benchmark  
**Port:** 3501  
**DB:** hybrid (PostgreSQL 16 Alpine + MongoDB 7)  
**Question:** How do PostgreSQL multi-table ACID transactions compare to MongoDB multi-document transactions and single-document embedded mutations in write latency, failure recovery, and code ergonomics when atomically mutating items, blockers, and events across all 8 domain invariants, and can PostgreSQL recursive CTEs match MongoDB `$graphLookup` on 5-level subtree rollups?

## Scenario

A team of developers with a C/C++ systems background is evaluating the core data architecture for Lerch. They must decide whether the production system should use a single relational database (PostgreSQL), a document database (MongoDB), or a hybrid split where spaces and actors live in SQL while items and events live in NoSQL (`§4.3 Q1`).

The developer launches the prototype and is presented with a diagnostic control plane running against both PostgreSQL and MongoDB. The system seeds the full domain model—implementing all 8 core invariant groups defined in `specs/data-foundation.md`:
1. `Space` (personal and organization contexts)
2. `Actor` (human users and autonomous agents)
3. `Item` (units of work at project, epic, story, and task scales)
4. `Hierarchy` (parent-child relations spanning up to 5 levels)
5. `Blocker` (severity triage and directed dependencies)
6. `Tag` (cross-cutting categorization)
7. `Artifact` (external links and file references)
8. `Event` (append-only audit log and notification stream)

Through the diagnostic interface, the developer explores three core operational workflows:

1. **Multi-Entity Atomic Mutation:** The developer triggers a composite business action: updating an item (`state`, `effort`, and score), establishing a directed blocker dependency with a 4-step severity scale, and appending an immutable audit delta to the event log. The developer can execute this under three distinct database transaction strategies:
   - *Strategy A (PostgreSQL Multi-Table Transaction):* Explicit `BEGIN ... COMMIT` wrapping `items`, `blockers`, and `events` tables with foreign key enforcement.
   - *Strategy B (MongoDB Multi-Document Session Transaction):* Multi-collection ACID transaction coordinated via MongoDB client sessions.
   - *Strategy C (MongoDB Embedded Single-Document Update):* Atomic update targeting an item document that embeds blocker severity and an inline events array.
   The developer can inject deliberate faults (e.g. unique constraint violations, malformed payloads, or simulated aborts) to inspect rollback guarantees and verify that zero partial writes occur.

2. **Blocker & Score Triage Lifecycle (`§2.3 Q3`):** The developer examines how an item's score and blocker severity are stored before and after triage. The interface compares an *un-triaged baseline* (where blocker severity and score reside as inline scalar attributes on the item) against a *triaged dependency model* (where blockers promote to first-class directed dependency records linking blocker and blocked items). The developer evaluates how each database engine handles this promotion and records the corresponding state transition in the event stream.

3. **5-Level Recursive Subtree Rollup:** The developer triggers a deep hierarchical calculation over a 5-level work breakdown tree (Space $\to$ Project $\to$ Epic $\to$ Story $\to$ Task $\to$ Subtask). The system aggregates total estimated `effort` and computes the worst-case (maximum) blocker severity propagating up the tree. The developer tests this on both a curated realistic baseline and synthetic datasets (1,000 and 10,000 items), directly comparing PostgreSQL's `WITH RECURSIVE` CTE against MongoDB's `$graphLookup` aggregation pipeline.

User authentication, WebSockets, rich text formatting, file uploads, and full Kanban boards are intentionally omitted to keep the prototype strictly focused on storage engine latency, transaction safety, and query ergonomics.

## What to Evaluate

### 1. Visual / Presentation Aspects (Diagnostic Tooling)
- **Schema & Invariant Inspector:** Side-by-side diagnostic views visualizing how all 8 domain invariants map to normalized relational tables (with foreign keys and junction tables) versus document collections (with embedded arrays and referenced ObjectIds).
- **Transaction Flow & Rollback Trace:** Step-by-step visual feedback displaying the execution sequence of atomic mutations, showing raw SQL statements (`BEGIN`, `UPDATE`, `INSERT`, `COMMIT`, `ROLLBACK`) alongside raw MongoDB command payloads (`startSession`, `withTransaction`, `commitTransaction`, `abortTransaction`).
- **Recursive Tree & Rollup Inspector:** A clear 5-level hierarchical tree view showing computed rollup values (`effort` sums and worst `blocker` severity) alongside individual node attributes, visually highlighting how impediments propagate up the branch.
- **Latency & Benchmark Visualization:** Side-by-side execution time comparisons (p50, p95 latency in milliseconds) and query plan metrics (`EXPLAIN ANALYZE` execution times and MongoDB `executionStats`) for write transactions and recursive reads.

### 2. Procedural / Workflow Aspects
- **Transaction Consistency & Fault Handling:** Experience of handling transaction rollbacks and partial failures in Node.js/Nitro when coordinating multi-entity updates. Assessing whether database drivers expose clear error boundaries analogous to structured error handling in systems programming.
- **Triage Promotion Workflow:** The operational steps required to transition an on-item blocker field into a directed dependency record. Evaluating whether schema migrations, event delta generation, and read queries feel cohesive or fragmented across relational vs. document models.
- **Benchmark Execution & Scale Switching:** Toggling between curated seed data and synthetic datasets (1k and 10k items) to observe how query performance and connection pool utilization scale under load.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **Engine Suitability (`§4.3 Q1`):** Does PostgreSQL handle flexible fields, event logs, and recursive hierarchy smoothly and fast enough (<10 ms at 10k items) to eliminate the operational complexity of a dual-engine hybrid architecture? Or does MongoDB's document model offer compelling latency and developer ergonomics for tree traversal and polymorphic event payloads?
- **Transaction Ergonomics:** Comparing the developer ergonomics of native PostgreSQL connection pool transactions (`pg.PoolClient`) against MongoDB session-based transactions (`MongoClient.startSession`). Evaluating connection checkout overhead, retry logic requirements, and Docker container footprint.
- **Hierarchical Query Mechanics:** Comparing the expressiveness, readability, and performance of SQL Recursive Common Table Expressions (`WITH RECURSIVE`) versus MongoDB `$graphLookup` aggregation pipelines for systems developers used to manual graph traversal in memory.
