# run-510: Bulk Import Validation, Transaction Modes & Multi-Format Export

**Kind:** benchmark  
**Port:** 3510  
**DB:** postgres  
**Question:** For bulk operations and data portability (DA2), how do all-or-nothing transactional imports compare to partial imports with dry-run previews on error recovery, batch insertion throughput, and duplicate prevention when ingesting 1,000+ item datasets in PostgreSQL, and how does streaming multi-format export (CSV, JSON, XML) perform under memory pressure?

## Scenario

A developer with a systems and C/C++ background is architecting the data portability and bulk operations engine (`DA2`) for Lerch. Real-world teams frequently migrate existing project data from spreadsheets or external issue trackers, or perform large-scale operational updates across hundreds of items. 

The developer opens the diagnostic workbench on port `3510` (`http://localhost:3510`) to resolve core backend questions surrounding bulk data ingestion, transaction boundaries, and streaming data export:

1. **Import Validation & Transaction Boundary Comparison (`§2.7 Q2`):**
   The developer tests ingesting synthetic 1,000-row CSV and JSON datasets containing deliberate bad records (missing required `title`, invalid `state` outside `unstarted`/`started`/`done`/`discarded`, unknown `kanban` column, and malformed date strings). The system evaluates two competing transaction strategies:
   - **Mode A (All-or-Nothing Transaction):** The entire batch executes within a single PostgreSQL transaction (`BEGIN ... ROLLBACK`). If any row fails validation or database constraints, the entire operation rolls back, leaving the database state pristine while returning a structured array of row-level errors (`{ row, field, value, reason }`).
   - **Mode B (Partial Import + Dry-Run Preview):**
     - *Dry-Run Preview:* Pre-validates the incoming payload entirely in memory without writing to the database, displaying a pre-flight summary of valid vs. invalid rows.
     - *Partial Ingestion:* Commits all valid rows in a batch transaction while skipping bad rows, generating a downloadable rejection file containing only the rejected records alongside their error annotations.

2. **The Re-Upload Recovery Dilemma & Duplicate Prevention:**
   The developer simulates the real-world user recovery cycle: after fixing the 20 rejected rows from a 1,000-row file, the user re-uploads the fixed file. The developer observes how naive partial imports cause duplicate records (re-inserting the 980 previously imported rows) unless an idempotency key (such as an external record ID, client UUID, or unique slug within space) or dry-run validation workflow is enforced.

3. **Streaming Multi-Format Export Engine:**
   The developer benchmarks exporting a space's item catalog (at 1k, 10k, and 50k item scales) across CSV, JSON, and XML formats. The system compares:
   - *Buffered Generation:* Assembling the full payload in Node process heap memory before sending HTTP headers.
   - *Chunked Streaming:* Pipelining database cursor rows through format encoders directly into the HTTP response stream (`Transfer-Encoding: chunked`), measuring Time-To-First-Byte (TTFB) and Node memory heap allocation.

4. **Batch Mutation API:**
   The developer tests executing bulk actions across selected items (moving 100 items to a target `kanban` column, transitioning their `state`, assigning a `tag`, or bulk deleting) comparing single parameterized SQL statements (`UPDATE items SET column = $1 WHERE id = ANY($2)`) against sequential queries.

Interactive Kanban drag-and-drop boards, full-text search indexing, OAuth authentication, and external webhook listeners are intentionally omitted to keep this prototype strictly focused on PostgreSQL transaction safety, validation pipeline ergonomics, and data streaming performance.

## What to Evaluate

### 1. Visual / Presentation Aspects (Diagnostic Tooling)
- **Import Error Inspector:** An interactive diagnostic table displaying ingestion failures with exact line numbers, target fields, offending values, and human-readable rejection reasons.
- **Dry-Run Pre-Flight Matrix:** A visual breakdown showing total rows, valid count, invalid count, and schema warning flags prior to database commit.
- **Streaming Telemetry & Memory Gauge:** Real-time metrics displaying Time-To-First-Byte (TTFB), total transfer duration, rows per second, and Node.js process heap memory consumption during 1k to 50k row exports.
- **Transaction Trace & Rollback Log:** Visual logs of the underlying SQL operations showing `BEGIN`, bulk `INSERT / UNNEST`, `ROLLBACK`, or `COMMIT` execution times.

### 2. Procedural / Workflow Aspects
- **User Recovery Friction on Re-Upload (`§2.7 Q2`):** Testing the operational workflow of correcting failed rows. Experiencing whether an all-or-nothing rejection (requiring fixing errors before any write occurs) or a partial import (with a downloaded rejection delta) creates less friction and lower risk of data corruption.
- **Idempotency & Duplicate Avoidance:** Evaluating how natural keys or external IDs prevent duplicate item creation when users repeatedly upload overlapping files.
- **Bulk Action Transaction Safety:** Observing failure modes during multi-item updates (e.g. if one item in a 100-item batch update is locked or belongs to another space) to confirm atomic consistency.

### 3. Technology / Stack Choices (Libraries, DX & Ergonomics)
- **Streaming Parser & Serializer Ergonomics:** Evaluating CSV/JSON/XML parsing libraries (such as `csv-parser` / `fast-csv` / `papaparse` and streaming XML writers) for Node.js/Nitro containers in terms of memory footprint, throughput, and error event handling.
- **PostgreSQL Batch Insertion Techniques:** Comparing performance across multi-row `INSERT INTO ... VALUES (...)`, PostgreSQL array unnesting (`INSERT ... SELECT * FROM unnest(...)`), and single-row looped queries for 1,000 to 10,000 item ingestion batches.
- **Transaction Rollback Semantics in Nitro:** Assessing how cleanly Nitro server routes and database connection pools (`pg.PoolClient`) handle transaction aborts, connection release, and structured HTTP error responses without leaking pool connections.
- **External Tool Data Mapping (`§2.10 Q4`):** Evaluating the minimal schema mappings required to ingest standard fields from common external tools (Jira, Trello, GitHub Issues CSV/JSON exports) into Lerch's core `Item` invariants (`title`, `state`, `kanban`, `effort`, `scheduled_time`).

## Done When

- [ ] `make seed RUN=510` seeds the PostgreSQL database with base spaces, actors, and baseline item fixtures idempotently without errors.
- [ ] Pre-packaged synthetic test datasets (1,000 rows clean, 1,000 rows with 2% invalid records, and 1,000 rows with 20% invalid records) are available for immediate execution via the web UI at `http://localhost:3510`.
- [ ] Ingesting invalid data in **Mode A (All-or-Nothing)** cleanly triggers a database rollback, leaving the items table unmodified and displaying a structured array of row-level errors (`{ row, field, value, reason }`).
- [ ] Ingesting invalid data in **Mode B (Partial + Dry-Run)** successfully provides a dry-run validation preview and allows committing valid records while generating a downloadable rejection file containing only the rejected rows.
- [ ] A duplicate detection / idempotency simulation demonstrates the outcome of re-uploading corrected files with and without unique key deduplication.
- [ ] Streaming export endpoint generates CSV, JSON, and XML downloads for 1k and 10k items, displaying side-by-side TTFB and server memory usage comparing buffered vs. streamed modes.
- [ ] Batch mutation endpoint executes atomic multi-item updates (`state`, `kanban` column, and batch deletion) using single SQL statements with execution timing reported in the UI.
- [ ] Repeated execution of `make seed RUN=510` on an active database remains completely idempotent.
- [ ] Scoped documentation (`docs/run-510/design.md`, `frontend.md`, `backend.md`, `NOTES.md`) is maintained.
